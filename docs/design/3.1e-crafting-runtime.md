# 3.1e — Crafting runtime seams (cap / failure / scaled cost, craft XP, crafting bench)

WP-3.1e is the crafting **correctness capstone**. The pure economics helpers already existed and were
tested (`UpgradeOutcomes`, `SocketOutcomes`, `ReforgeOutcomes`, `CraftXp`/`CraftXpSource`), and the
generic engine (`CraftEngine` / `CraftingServiceImpl`) already *applied* every `OutcomePlan.Modify` — but
it applied the **raw** plan: upgrades bumped `upgradeLevel` with no cap and no chance of failure, socket
cuts appended past any limit, and every craft charged the **static conf cost**. This WP wires the helpers
into the live craft through **one per-outcome runtime step** and ships a crafting bench so the
material-refine recipes are craftable. No API change, no schema change, no new engine branch.

## The one mechanism, preserved: `CraftRuntime.effectiveCraft`

The per-kind rules live in a single **pure dispatch table**, `core/crafting/CraftRuntime.kt`, *not* as
bespoke branches scattered through `applyCraft`:

```
effectiveCraft(outcome, plan, target, rarity, confCost, seed): EffectiveCraft
  where EffectiveCraft = { status: SUCCESS|FAILURE|REJECTED, cost, resultData?, rejection?, message? }
```

| Outcome kind | Helper reused | Cost | resultData | Status / message |
| --- | --- | --- | --- |
| `UpgradeInput` | `UpgradeOutcomes` | rarity-scaled `upgradeGoldCost` (+ `RarityRules.upgradeXpCost`) on success; failure gold fraction, 0 XP on failure | capped upgraded instance on success; **unchanged** target on failure | at cap → `REJECTED(INVALID_TARGET)` + `upgrade.at_cap`; else `SUCCESS`/`FAILURE` + `upgrade.success`/`upgrade.failure` |
| `AddSocket` | `SocketOutcomes` | `addSocketCost(existingSlots)` | the plan's appended-sockets instance | over cap → `REJECTED(INVALID_TARGET)` + `socket.cap_reached`; else `SUCCESS` |
| `Reforge` | `ReforgeOutcomes` | `reforgeCost(rarity)` | the plan's reforged instance | `SUCCESS` |
| `Repair` / `InsertGem` / `RemoveGem` / `Enchant` / `NewItem` / `Transmute` | — | conf cost | the plan's `Modify` result, or `null` for a fresh-item `Create` | `SUCCESS` |

Every arm that adds no rule falls through `passthrough` to *plan result + conf cost*, so the runtime is a
strict, additive refinement of the engine, never a fork. `effectiveCraft` is a pure function of the
outcome, the pre-computed `OutcomePlan`, the target instance, its `Rarity` and the craft `seed` — no
Bukkit, no server — so `CraftRuntimeTest` asserts the whole cap/failure/cost model off-server. (The one
non-primitive field, `EffectiveCraft.message`, is an Adventure translatable `Component`, which the pure
crafting helpers already build off-server.)

### How `craft()` consults it

`CraftingServiceImpl.craft()` keeps R1 (inline, one synchronous unit — never a scheduler hop) and R2
(validate before any side effect):

1. Plan (`CraftPlanner.plan`) and the existing generic validation (`validateApplication`) run first.
2. `effectiveCraft(...)` produces the verdict, resolving the target's rarity from its `ItemDefinition`.
3. **`REJECTED`** → relay `message` (if any) and return `CraftResult.Failure(rejection)`. Nothing is
   consumed, because the station menu only drains the escrow on `Success`.
4. Funds are gated on the **effective** (rarity-scaled) cost — before any side effect.
5. **`SUCCESS`/`FAILURE`** → fold the verdict back onto the result (`OutcomePlan.Modify(resultData)` +
   effective cost), apply inline via the unchanged two-arm engine, relay `message`, grant craft XP.

## Upgrade failure / at-cap and the escrow interaction

The station menu consumes the deposited reagents **only** on `CraftResult.Success`, in the same
synchronous unit as `craft()`. That drives the three upgrade outcomes:

- **Success** → `Success`. Reagents consumed, item upgraded (capped), full rarity-scaled gold + XP
  charged. Player sees `ramrpg.crafting.upgrade.success`.
- **Failure** (rolled above the safe threshold) → still `Success`. The attempt *happened*: reagents
  consumed and only the `FAILURE_GOLD_FRACTION` charged, but the item is returned **unchanged**. Player
  sees `ramrpg.crafting.upgrade.failure`.
- **At cap** → `Failure(INVALID_TARGET)`, so the menu keeps the reagents (**nothing consumed**). Player
  sees `ramrpg.crafting.upgrade.at_cap`. A socket cut over the slot cap is the same shape
  (`socket.cap_reached`).

`INVALID_TARGET` is the frozen-API failure the at-cap/over-cap rejects map to (there is no `AT_CAP` enum,
and the API is frozen). The **specific** feedback comes from `CraftRuntime` selecting the translatable
`Component`, which `craft()` relays via `player.sendMessage(...)` — chat, deliberately not the action bar,
so it is not overwritten by the menu's generic result line that fires after `craft()` returns. All lang
keys already exist (WP-3.3a/3.3d); **no new lang keys** were added.

## Cost scaling

The static `cost { … }` in each `.conf` is a fixed baseline (a recipe cannot know the target item's
rarity). `effectiveCraft` substitutes the rarity-scaled charge for the three kinds that scale — money via
the outcome helper, and for upgrades the XP-level half via the pre-existing `RarityRules.upgradeXpCost`
ladder, so both halves track the same rarity. Passthrough kinds keep their conf cost unchanged.

## Craft-XP trigger

Fired at the apply-success point in `craft()`:
`CraftXpSource.forCraft(recipe, result, tier = 1)?.let { skillService.addXp(player, it) }`
(`skillService` is already a constructor dependency — no new wiring, and `NonCombatXpListener` is
untouched). Decisions:

- **On `SUCCESS` only.** A rolled upgrade `FAILURE` still consumes reagents but grants no XP — a failed
  attempt teaches nothing. (`REJECTED` never reaches this point.)
- **`tier = 1`** until `ItemDefinition.tags` is surfaced as the material-tier seam (`CraftXp` already
  takes tier as a pure input; only the caller-side resolution is deferred).
- `forCraft` returns `null` unless the recipe drives a skill (a `NewItem`'s `qualitySkill`), so
  upgrade/socket/reforge grant no craft XP today; the seam is generic and needs no per-kind branch.

## Crafting bench (the NEW_ITEM gap)

The 3.1a model gives the **crafting/transmute bench** the item-*creating* kinds `{NEW_ITEM, TRANSMUTE}`,
while smithing owns the item-*transforming* kinds. The refine recipes in `content/recipes/materials.conf`
are all `new_item`, so at the smithing table they were `DISALLOWED_OUTCOME`. This WP:

- ships `content/stations/crafting_bench.conf` (`id ramrpg:crafting_bench`, `blocks=["CRAFTING_TABLE"]`,
  `permitted-kinds=["NEW_ITEM","TRANSMUTE"]`) and adds it to `RpgContentLoader.PACKAGED_CRAFTING_CONTENT`;
- **re-points** the refine recipes' `station` from `ramrpg:smithing` to `ramrpg:crafting_bench`, so they
  are craftable.

`NEW_ITEM` is deliberately **not** added to smithing (that would break the "smithing owns transforming
outcomes" model).

## Deferred

- The recipe-book opener is a follow-up (not wired here).
- Real tiered craft XP awaits `ItemDefinition.tags` (tier resolution); `tier = 1` until then.
- A live apply/XP/menu integration test stays M10-blocked (no `MenuClickContexts` fake in RamCore); the
  hard logic is kept in the pure `CraftRuntime` so it is fully testable without one.
