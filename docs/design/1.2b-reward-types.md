# 1.2b — Reward types and parameters

RamRPG registers four `RewardActionFactory` types into RamCore's `RewardActionFactories` registry
(`RamRPG.rewardFactories`, built from `RewardActionFactories.standard(economy.ramCoreEconomy)` so the
built-in `money`/`command`/`message`/`permission-node-check` factories are still present). Nothing
consumes this registry yet: `QuestService` still carries its own `QuestReward` model
(`api/quests/Quests.kt`), unchanged by this WP. A later WP re-models quest rewards onto
`RewardPlan`/`RewardActionFactories` and will be the first real consumer.

## `skill_xp`

Grants a fixed amount of XP in one skill through `SkillService.addXp`.

| param    | type   | required | notes |
| -------- | ------ | -------- | ----- |
| `skill`  | string | yes      | a `ContentId` (`namespace:value`, e.g. `ramrpg:combat`); a bare id without a namespace is rejected |
| `amount` | double | yes      | must be `> 0` |

The XP grant runs under an ad-hoc `XpSource` keyed `ramrpg:reward` (`XpSourceKey.of("ramrpg", "reward")`) so it is
distinguishable from other XP sources (combat, quests, non-combat activities) if that ever matters for
analytics or anti-abuse. No default amount is provided — a reward with no XP would be a content bug, so it
is a load-time error instead of a silent 0.

## `rpg_item`

Gives a freshly-rolled `ItemInstanceService.create` instance of a registered `ItemDefinition` — not a
shared static `ItemStack` template — because each grant should get its own `instanceId` and, if the
definition has `statRolls`, its own independent roll. This is why `rpg_item` exists at all:
RamCore's built-in `item` reward action takes one pre-built `ItemStack` and clones it for every
execution, which is right for a generic reward item but wrong for an RPG item whose per-instance
identity and rolled stats matter.

| param   | type   | required | notes |
| ------- | ------ | -------- | ----- |
| `item`  | string | yes      | an `ItemKey`'s `ContentId`, must already be registered in `ItemDefinitionRegistry` |
| `count` | int    | no       | default `1`; must be `> 0` when given |

**Ordering caveat (recorded, not fixed here):** the item lookup happens at `create()` time, i.e. at
content-parse time, so a `rpg_item` reward can only reference items that are already registered when
the reward content loads. In the current plugin, `registerBuiltins()` (which registers every builtin
`ItemDefinition`) runs before `registerListeners()` (where `rewardFactories` is built), so this is safe
today. Once Task 1.5 (`ContentLoader`) lands and reward content can be reloaded independently of item
content, load ordering between the two content types will need to be either enforced or the item lookup
deferred to `apply()` time. Flagged here rather than solved, since RamRPG has no content-loading
pipeline yet for this WP to hook into.

## `buff` and `perk_point` (stubs)

Neither `BuffService` (WP-4.1a) nor a perk system (WP-5.1a) exists yet. Both factories still parse and
validate their expected shape — so content authored now survives unchanged once the real systems land —
but the `RewardAction` they build always fails `validate()`, via a shared `UnimplementedRewardAction`.

Because `RewardEngine.run()` collects `validate()` errors from **every** entry in a plan (guaranteed and
weighted) before executing any of them, a single `buff` or `perk_point` entry blocks the *entire*
containing reward plan from running — not just that one entry. This is deliberate (WP-1.2b rule 8: fail
loud, never silently no-op) and is the reason neither stub is wired into any shipped content by this WP.

`buff` params (shape only; not yet applied):

| param            | type   | required | notes |
| ---------------- | ------ | -------- | ----- |
| `buff`           | string | yes      | a `ContentId` naming the buff |
| `duration_ticks` | int    | no       | default `200` (10s); must be `> 0` when given |
| `stacks`         | int    | no       | default `1`; must be `> 0` when given |

`perk_point` params (shape only; not yet applied):

| param    | type   | required | notes |
| -------- | ------ | -------- | ----- |
| `points` | int    | no       | default `1`; must be `> 0` when given |
| `tree`   | string | no       | a `ContentId` naming the perk tree; omitted means the general tree |

## Folia safety

Every factory's `create(ConfigurationNode)` only parses and validates; it never touches a live player,
inventory, or Bukkit scheduler. Each `RewardAction`'s `apply()` resolves the online player subject via
`RewardSubjects.onlinePlayer`, then dispatches the actual mutation (XP grant, inventory add) onto that
player's `TaskContext` through `PlatformScheduler.runForPlayer` — never inline, never on a raw Bukkit
scheduler — and returns `RewardOutcome.success` immediately once dispatched. `money` (from RamCore's
`standard()` factories) stays synchronous because `Economy` implementations are thread-safe by contract;
`skill_xp` and `rpg_item` are not, hence the hop.
