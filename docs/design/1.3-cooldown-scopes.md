# 1.3 — Ability cooldown scopes and persistence

Ability cooldowns are backed by RamCore's `cooldown.CooldownTracker` instead of a hand-rolled
timestamp map (`AbilityServiceImpl`). One `CooldownTracker<CooldownKey>` per ability, created lazily
with that ability's duration as its base (`Cooldown.ofTicks(ability.cooldown.ticks)`).

## Scope key strategy

`Cooldown(ticks, keyScope)` on an ability declares its `CooldownScope`. The tracker key is a
`CooldownKey(group = ability id, key = scope discriminator)`:

| Scope | Discriminator | Meaning |
| --- | --- | --- |
| `PLAYER` | player UUID | per-player cooldown (default) |
| `ITEM` | item instance id | per-item-instance cooldown; **falls back to the player UUID** when the instance id is null (`assignInstanceId = false`), never a shared null key |
| `GLOBAL` | constant `"global"` | one cooldown shared by all players |

## API

`AbilityService.remaining(player, ability): Duration` returns the time left (or `Duration.ZERO` when
ready). For `ITEM` scope it uses the player-fallback key, because no held item is known at that entry
point; lore/HUD that has the item computes the item key itself. `formatCooldown(Duration)` renders it
as `"0s"` / `"3.2s"` / `"45s"` / `"1m 5s"` for the on-cooldown message and later HUD/lore.

## Cooldown lifecycle

- Gate: `tracker.peek(key).denied()` (a non-consuming check) → the fire is refused with
  `ramrpg.ability.on_cooldown` carrying the remaining time.
- Start: only after a successful `execute`, `tracker.test(key)` starts the cooldown from now — a
  failed cast (wrong tool, refunded mana) does not start it.

## Persistence

Not persisted today: `CooldownTracker` is in-memory, so cooldowns reset on restart. This is
acceptable for ability cooldowns (short, gameplay-scoped). If a future WP needs cooldowns to survive
a restart, `Cooldowns.grouped(cooldown, store)` accepts a `CooldownStore<CooldownKey>` backed by the
Stores API with `CooldownKey.keyCodec()` — wire it there rather than reintroducing a bespoke map.

## Not hot-swappable

The cooldown *duration* is captured when a tracker is first created for an ability. A `/rpg reload`
that changes an ability's cooldown does not retune already-created trackers until restart; document
this in the reload semantics (WP-1.5c).
