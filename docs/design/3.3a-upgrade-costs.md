# 3.3a — Upgrade cost curve and failure thresholds

WP-3.3a makes smithing **upgrade** recipes real content: they raise a placed item's
`ItemInstanceData.upgradeLevel` in exchange for tiered reagents and gold, above a failure threshold, and
never past a per-rarity cap. It ships **content + pure economics only** — the generic craft engine
(WP-3.1b) already *applies* the upgrade, so nothing in the engine changed.

## Where each piece lives

| Piece | Home | Note |
| --- | --- | --- |
| Applying `upgradeLevel + n` | 3.1b `CraftingServiceImpl` (unchanged) | 3.1a `RecipeOutcome.plan` collapses `UpgradeInput` to one `OutcomePlan.Modify`; the engine writes it through its one `ModifyTarget` arm. |
| The recipes | `content/recipes/smithing_upgrade.conf` | `type = upgrade_input` outcomes; item-id-gated reagents; `cost { money, experience-levels }`. |
| Gold curve, failure model, cap check | `core/crafting/UpgradeOutcomes.kt` (pure) | The smithing-specific economics the raw outcome does not model. |
| XP-level curve | `api/items/RarityRules.upgradeXpCost` (pre-existing) | Reused, not forked. |
| Gold charging | `core/listeners/EconomyService.charge/canAfford` | Vault-absent ⇒ free, never blocked. |

An upgrade's **only** gameplay effect is the higher `upgradeLevel`: `EquipmentStatProvider` already scales
base stats and rolls by `1 + upgradeLevel * 0.05`, so no bespoke stat path is introduced.

## Cost model

Two axes are charged per step, both cumulative over a run of upgrades:

- **XP levels** — the existing `RarityRules.upgradeXpCost(from, to)`, which sums `2 + n` per level `n` and
  is then rarity-weighted by `upgradeCostMultiplier`.
- **Gold** — new in `UpgradeOutcomes`:

```
GOLD_PER_LEVEL = 100.0
goldForStep(n)          = 100 * n                     # reaching level n from n-1 (0 for n <= 0)
upgradeGoldCost(f, t)   = Σ goldForStep(n), n in (f+1)..t   # 0 when t <= f
upgradeGoldCost(f,t,r)  = ceil(upgradeGoldCost(f, t) * RarityRules.upgradeCostMultiplier(r))
```

Per-step gold is **linear** in the level reached, so cumulative gold grows **triangularly** — late upgrades
are the expensive ones, matching the failure ramp. Rarity multipliers reuse `RarityRules`
(COMMON 1.0 … MYTHIC 8.0), so a mythic +1 costs 8× a common +1.

Worked values (base, COMMON): `0→1 = 100`; `0→3 = 100+200+300 = 600`; `5→8 = 600+700+800 = 2100`.
Rarity-weighted `0→1`: COMMON 100, RARE 200, MYTHIC 800.

The static `cost { money }` in each recipe is the **entry fee** for the first step at that recipe's
representative rarity; the live runtime scales the true charge with `upgradeGoldCost(current, target,
rarity)`.

## Failure model

Roadmap 3.3: *"failure chance above a threshold that consumes materials but not the item."*

```
SAFE_UPGRADE_LEVEL   = 5      # reaching level <= 5 never fails
FAILURE_PER_LEVEL    = 0.08
MAX_FAILURE_CHANCE   = 0.75
failureChance(t)     = 0                                          if t <= 5
                     = min(0.08 * (t - 5), 0.75)                  otherwise
```

So `+6 = 8%`, `+10 = 40%`, `+15 = 75%` (the ceiling; `0.08 * 10 = 0.80` clamps to `0.75`). The decision is
`isFailure(toLevel, seed)`, a splitmix64 uniform `< failureChance` over a **distinct** salt (deliberately
not `QualityRoll.CRIT_SALT` nor the splitmix64 increment) — deterministic, and independent of
`QualityRoll`'s quality/crit rolls on the same craft seed so a crit craft is not also a forced failure
(`UpgradeSaltIndependenceTest`).

On the outcomes of one attempt (`UpgradeOutcomes.resolve` → `UpgradeResolution`):

| Attempt | Item written | Reagents | Gold charged |
| --- | --- | --- | --- |
| **Success** | `upgradeLevel = cappedTargetLevel` | consumed | full `upgradeGoldCost` |
| **Failure** | **unchanged** (item spared) | **consumed** | `FAILURE_GOLD_FRACTION` (0.25) of full |
| **At cap** | unchanged | not consumed | 0 (craft refused) |

A failed upgrade therefore **burns the materials and a 25% gold fee but never loses, downgrades, or
corrupts the item** — the safe-failure model the roadmap asks for.

## Cap

The per-rarity ceiling is the pre-existing `RarityRules.upgradeCap` (COMMON 5, UNCOMMON 7, RARE 10, EPIC
12, LEGENDARY 15, MYTHIC 20). `UpgradeOutcomes` wraps it so runtime and tests read one source:
`isWithinCap`, `isAtCap`, `cappedTargetLevel` (clamps `current + levels` to the cap, never below current).
An at-cap attempt is refused before anything is consumed; an over-shooting step is clamped to the cap.

## Player-facing strings

`lang/en_us.json` gains `ramrpg.crafting.upgrade.{success,failure,cost,at_cap}`, built as Adventure
components by `UpgradeMessages` for the live runtime to show. `cost` carries `{0}` gold and `{1}` XP-level
placeholders.

## Tuning status

`GOLD_PER_LEVEL`, `SAFE_UPGRADE_LEVEL`, `FAILURE_PER_LEVEL`, `MAX_FAILURE_CHANCE` and `FAILURE_GOLD_FRACTION`
are placeholders in the spirit of the 0.1 power curve — tuned alongside crafting content (roadmap 3.2). A
future knob may let a smithing skill reduce `failureChance`; today failure keys off the target level only.
