# 2.2 — Durability drain, inert-at-zero, never breaks

WP-2.2 implements decision D2 ([0.1 durability](0.1-durability.md)): durability **DRAINS on use**, and at
`0` the item goes inert via WP-2.1c's existing `InertReason.ZERO_DURABILITY` path — it is **never broken
or deleted**. This WP owns exactly three things: the pure `DurabilityService.damage`/`repair` operations,
the combat-pipeline stage that actually drains a stack's durability, and suppressing the vanilla event only
for recognized RPG items. Repair (the sink) is WP-3.3b — `repair()` exists now, pure, but nothing calls it.

## Durability drain rates and repair costs

| Event | Rate | Where it is wired |
| --- | --- | --- |
| Weapon hit lands (attacker's held item) | `DurabilityService.DRAIN_PER_HIT = 1` | `DurabilityDrainStage` at `DamagePriority.APPLY` (2000), `builtin/stats/DamageStages.kt` |
| Armor takes a hit (per equipped piece, victim) | `DurabilityService.DRAIN_PER_ARMOR_HIT = 1` | same stage, same priority |
| Tool breaks a block | `DurabilityService.DRAIN_PER_BLOCK_BREAK = 1` | **documented only, not wired** — see below |
| Repair cost formula | — | **placeholder, deferred to WP-3.3b** — the smithing station decides reagent/money cost; `DurabilityService.repair(data, amount)` is the pure sink it will call |

Rates are flat integers per event, not damage-proportional — this mirrors vanilla's roughly-fixed
per-swing/per-block durability loss (before Unbreaking's random skip) rather than scaling with
`ctx.finalDamage`, so a heavily-mitigated hit (e.g. armor reducing damage to near zero) still costs the
victim's armor durability exactly like a full-damage hit would: the armor did its job, which is what
durability is charging for. `maxDurability` itself is still the WP-2.1b placeholder
(`ItemInstanceData.DEFAULT_MAX_DURABILITY = 500`); at `1`/hit that is roughly the lifetime of a vanilla
unenchanted tool, which is a reasonable placeholder pending real tuning (per-item `maxDurability` and
faster/slower drain per weapon tier is a follow-up balance pass, not this WP).

**Why weapon *and* armor, not just the weapon.** The roadmap prompt says "attacker's weapon (and/or
victim's armor per your documented model)" and leaves the choice to this WP. Draining only the weapon
would make armor durability a dead field forever (nothing else touches it before WP-3.3b), so both sides
drain through the identical `DurabilityService.damage` call — one mechanism, both directions, no bespoke
armor-only code path.

**Why block-break is documented but not wired.** This WP's file scope is exactly
`DurabilityListener.kt`, `DamageStages.kt`, and this new `DurabilityService.kt` — there is no
`BlockBreakEvent` listener in scope to attach tool-use drain to, and adding a new listener file is outside
the exhaustive file list. `DurabilityService.DRAIN_PER_BLOCK_BREAK` exists so a future WP (or the
orchestrator, if trivial) has the rate ready to call `DurabilityService.damage(data,
DurabilityService.DRAIN_PER_BLOCK_BREAK)` from a `BlockBreakEvent` handler without inventing a new number.
Until then, RPG pickaxes/axes/shovels/hoes do not lose durability from breaking blocks — a known,
deliberate gap (rule 9: stay inside this WP; adjacent breakage is reported, not fixed here).

## The never-breaks / inert-at-zero model

- `DurabilityService.damage(data, amount)` clamps `durability` to `[0, maxDurability]` — it can reach `0`
  but never goes negative, and the `ItemStack` itself is never removed, downgraded, or replaced with air.
  Draining an already-zero instance is a stable no-op (`DurabilityNeverBreaksTest`).
- Once `durability <= 0`, WP-2.1c's `ItemDefinition.inertReason(instance, state)` already returns
  `InertReason.ZERO_DURABILITY` (`api/items/Items.kt`) — every item-based `StatProvider`
  (`EquipmentStatProvider`, `EnchantmentStatProvider`, `ReforgeStatProvider`, `SocketStatProvider`) already
  consults that shared check and withholds its contribution. **This WP does not re-implement or duplicate
  that check anywhere** — `DurabilityDrainStage` and `DurabilityService` only make the number reach `0`;
  `DurabilityZeroIsInertTest` asserts the transition (via `inertReason`/`isInert`), not a re-derivation of
  what "inert" means. The item's lore already renders the RED `Durability` line + inert banner at zero
  (WP-2.1c's `LoreRender.durability`) with no change needed here.
- `ramrpg.item.broken` is sent to the item's owner exactly once, on the hit that brings `durability` from
  `>0` down to `0` (not on every subsequent hit against an already-broken item — `DurabilityDrainStage`
  skips draining/notifying once `data.durability <= 0`). It is flavour text on top of the lore banner, not
  a second inert mechanism.

## Why RPG items cancel the vanilla event, and non-RPG items don't

`DurabilityListener` used to cancel `PlayerItemDamageEvent` unconditionally for every item on the server.
It now calls `ItemInstanceService.identify(event.item)` — the same "is this an RPG item" check
`EquipmentStatProvider`/`EnchantDamageStage`/etc. already use — and cancels the event **only** when that
returns non-null. A plain vanilla item (a stick, an un-registered iron sword) is untouched and keeps
exactly the durability behaviour it always had.

RPG items are cancelled here because their durability is driven entirely by `DurabilityService` through
`DurabilityDrainStage`, not by Bukkit's own damage-event math — running both would double-drain (once from
vanilla's own logic, once from our stage) and let vanilla eventually *break and delete* the stack, which
directly violates the never-breaks rule this whole WP exists to guarantee.

### RamRPG.kt wiring gap (orchestrator TODO at merge)

`DurabilityListener`'s only construction call site is `RamRPG.kt`: `DurabilityListener().register(this)`.
This WP's file scope (rule 8 / B5) forbids editing `RamRPG.kt`, so — following the exact pattern WP-2.1c
used for `ItemRequirementServices` — the constructor takes `items: ItemInstanceService? = null` as an
optional trailing parameter, keeping that call site compiling unchanged. When `items` is `null` (today,
until wired), the listener falls back to cancelling **every** `PlayerItemDamageEvent`, i.e. exactly the
blanket-cancel behaviour this file shipped with before WP-2.2 — a deliberate fail-safe default, not a
regression, but also not this WP's actual goal (non-RPG items keeping vanilla durability). At merge:

```kotlin
DurabilityListener(itemInstances).register(this)
```

`itemInstances` is already resolved in `RamRPG.kt` for other services, so this is a one-line change.

### CombatModule.kt (outside the strict file list, added per rule 8)

`DurabilityDrainStage` needs `ItemInstanceService` at construction, and (per rule 4 — Folia-safe pipeline
context, no raw scheduler) it must run as a registered `DamageStage`, not a listener. `CombatModule.kt`
already resolves `itemInstances` from the `ServiceContext` for the other builtin stages and is the module
rule 8 names as the intended home ("if the stage is a builtin registered in CombatModule, add it there") —
so it registers `DurabilityDrainStage(itemInstances, DurabilityService())` alongside `ApplyStage()`.
`DurabilityService` itself is stateless and constructed inline; it needs no `RpgServiceKeys` entry. This is
a fourth touched file beyond the exhaustive three (`DurabilityListener.kt`, `DamageStages.kt`,
`DurabilityService.kt`) — the same kind of scope note WP-2.1c made for touching
`ReforgeStatProvider.kt`/`SocketStatProvider.kt`: in service of the literal DONE criterion (the stage must
actually run in the live pipeline), not a substitute for it. No `RamRPG.kt` edit was needed for this part.

## Folia-safety

`DurabilityDrainStage.apply` mutates the attacker's main-hand slot and the victim's worn armor slots
directly (`inventory.setItemInMainHand`, `equipment.helmet = ...`, etc.) with no `PlatformScheduler`/raw
Bukkit scheduler hop — the same pattern `LifestealStage` already uses for `p.health`. `DamagePipeline.
process` runs synchronously inside `CombatListener`'s `EntityDamageByEntityEvent` handler, which Folia
already dispatches on the entity's own region thread, so writing back to that same entity's inventory here
is already running in the correct region — there is nothing left to schedule.

## Testable-without-a-server

Per rule 10 and the "pure, off-server" requirement, all three required tests exercise
`DurabilityService`/`ItemInstanceData`/`ItemDefinition.inertReason` directly — none construct a live
`Player`/`ItemStack`/inventory:

- `DurabilityDrainOnHitTest` — `damage()` reduces durability by the drain amount; N applications lose
  `N * DRAIN_PER_HIT`.
- `DurabilityZeroIsInertTest` — draining to `0` flips `ItemDefinition.inertReason` to
  `InertReason.ZERO_DURABILITY` and `isInert` to `true`; one representative `equipmentStatsFor` call
  confirms zero stat contribution without re-covering WP-2.1c's full provider matrix
  (`InertItemContributesNoStatsTest` already owns that).
- `DurabilityNeverBreaksTest` — draining arbitrarily far past `0` clamps at `0`, never negative; draining an
  already-zero instance is a stable no-op; every other `ItemInstanceData` field survives a drain-to-zero
  unchanged (identity, upgradeLevel, customName, maxDurability).

The live guarantees these back — the vanilla event actually getting cancelled for an RPG item in someone's
hand, the drained stack actually re-appearing in the inventory slot, the lore actually greying out in a
client's hotbar — need a live Paper/Folia server and are covered by
[docs/SMOKE_TEST.md](../SMOKE_TEST.md) row 9 instead.
