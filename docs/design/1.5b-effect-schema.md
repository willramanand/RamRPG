# 1.5b — Effect schema, builtin action/condition/matcher ids

WP-1.5b makes `dev.willram.ramrpg.api.effects.Effect` serialisable from HOCON and gives
`TriggeredEffect` a dispatcher. Every later system that expresses gameplay — perks, sets, buffs,
affixes, enchants — serialises through the schema recorded here.

> This note is intentionally NOT linked from `docs/DESIGN.md`; the orchestrator regenerates that index
> at merge (execution-plan F.3 step 5a), so `DesignSectionCoverageTest` is expected to be red on the
> `wp/1.5b` branch and only this branch. It is the sole expected failure.

## The three effect forms

An `effects = [...]` bundle sits on an item or enchant. Each element is one `Effect`, chosen by `type`:

| `type` | HOCON fields | Produces |
| --- | --- | --- |
| `stat` | `stat` (id), `op` = `ADD` \| `MULTIPLY_BASE` \| `MULTIPLY_TOTAL` (default `ADD`), `amount` (scaling) | `StatEffect` |
| `damage_stage` | `stage` (named priority or int), `action` (id), `params` | `DamagePipelineEffect` |
| `triggered` | `trigger` (grammar below), `conditions` (list), `action` (id), `params` | `TriggeredEffect` |

An effect's `key` (`EffectKey`) is its optional `key` field, else a stable synthesised
`<owner-namespace>:<owner-value>_fx<index>` (owner = the item/enchant id).

### Scaling (`amount`), reusing the api `Scaling` factory

| HOCON | Formula | Evaluated with holder level `L` |
| --- | --- | --- |
| `amount = 5.0` (scalar shorthand) | `Scaling.flat` | `5.0` |
| `amount { flat = 5.0 }` | `Scaling.flat` | `5.0` |
| `amount { linear = 3.0 }` | `Scaling.linear` | `3.0 · L` |
| `amount { linear_with_base { base = 2.0, per_level = 0.5 } }` | `Scaling.linearWithBase` | `2.0 + 0.5 · L` |

Level enters at *apply* time through `ScalingContext.level` (a `StatEffect`'s amount is a
`ScalingFormula`, evaluated with the holder's level), so `RPGEnchantment.effects(level)` returns the
parsed bundle unchanged — matching the Kotlin builtins (e.g. `Critical` uses `Scaling.linear`).

### `damage_stage` priorities

`stage` accepts any raw integer priority or a named `DamagePriority` constant (case-insensitive):
`WEAPON_BASE, STRENGTH, ENCHANT_OFFENSE, EFFECT_OFFENSE, CRIT_ROLL, ELEMENTAL_BREAKDOWN, ABILITY_MOD,
ARMOR_MITIGATION, TRUE_DEFENSE, ENCHANT_DEFENSE, SHIELDS, THORNS, LIFESTEAL, FEROCITY, INDICATOR,
APPLY`. This is a fixed grammar (a data lookup map), not an extensible registry.

A `damage_stage` reuses the **same** `action` vocabulary as `triggered`: `EffectActionRegistry.damageHook`
wraps the resolved `EffectAction` in a `DamageStageHook` that runs it with an `EffectContext` built from
the live `DamageContext`. This one-vocabulary-two-surfaces design is why the WP ships **three**
registries (actions, conditions, block-matchers), not four.

## The nine trigger grammar

`trigger` is a string; the arg (if any) follows the FIRST `:` (so a `custom`/`on_block_break` arg may
itself be a `ns:value` id). The nine forms map one-to-one to the `EffectTrigger` sealed hierarchy — a
closed grammar, so parsing it is a `when`, not a registry (only this WP / an api change touches it).

| Form | Arg carried how | `EffectTrigger` |
| --- | --- | --- |
| `on_equip` | — | `OnEquip` |
| `on_hit` | — | `OnHit` |
| `on_hurt` | — | `OnHurt` |
| `on_kill` | — | `OnKill` |
| `on_interact:<LEFT\|RIGHT\|SHIFT_LEFT\|SHIFT_RIGHT>` | enum after `:` → `InteractType` | `OnInteract(type)` |
| `on_block_break:<matcher-id>` | `ns:value` after `:` → `BlockMatcherRegistry.require` | `OnBlockBreak(matcher)` |
| `tick` | — | `Tick` |
| `on_consume` | — | `OnConsume` (added by this WP) |
| `custom:<content-id>` | `ns:value` after `:` → `ContentId` | `Custom(id)` |

`on_consume` is the sanctioned api change: a purely-additive `data object` on the sealed hierarchy (no
existing case removed/renamed, so no `@Deprecated(ReplaceWith)` cycle). Task 4.2 (potions) is its first
intended consumer.

## Builtin id tables (DATA in registries, never `when` branches)

The **only** knowledge of these ids lives in `BuiltinEffectActions` as `register(...)` calls. A new
action/condition/matcher is added by registering an id, never by editing a branch. An unknown id raises
a `ContentDeserializeException` naming it, which the SpecLoader aggregates as a source-tagged
`ValidationError`.

### `EffectActionRegistry` (id → `EffectAction` factory)

| id | `params` | Effect on execution |
| --- | --- | --- |
| `ramrpg:heal` | `amount` (double, def 1.0) | Heals the acting entity, capped at its max health |
| `ramrpg:message` | `text` (MiniMessage, required) | Sends the line to the acting player |
| `ramrpg:ignite` | `ticks` (int, def 40) | Sets the target on fire (never shortens an existing burn) |

### `EffectConditionRegistry` (id → `Condition` factory)

| id | `params` | Passes when |
| --- | --- | --- |
| `ramrpg:always` | — | always |
| `ramrpg:sneaking` | — | the acting player is sneaking |
| `ramrpg:has_target` | — | a target entity is present |
| `ramrpg:chance` | `chance` (0.0–1.0, def 1.0) | a random roll < chance |

### `BlockMatcherRegistry` (id → `BlockMatcher`)

| id | Matches |
| --- | --- |
| `ramrpg:any` | any block (`BlockMatchers.ANY`) |
| `ramrpg:ores` | vanilla ores + deepslate/nether variants (`BlockMatchers.ofMaterials`, entry one) |
| `ramrpg:logs` | all log/stem types |
| `ramrpg:crops` | wheat, carrots, potatoes, beetroots, nether wart |

The set is deliberately small: enough to prove "content is data" end-to-end, without pre-building
later WPs' content (no potion/buff/perk actions).

## Dispatcher and TaskContext per trigger (Folia)

`TriggeredEffectDispatcher` separates a **pure** routing core (`dispatch(kind, ctx, …)` — unit-tested
off-server) from Bukkit wiring (`bind(consumer)`). Every subscription and the tick task binds to the
`ContentModule` `TerminableConsumer` (RamCore tears them down on disable — rule 4), which is exactly why
the dispatcher binds through a `TerminableModule` and never through `RamRPG.kt` (B5).

Each handler reads what it needs on the event thread, then dispatches on the acting entity/player's
scheduler via `PlatformScheduler` (RamCore `Schedulers`):

| Trigger | Bukkit source | Subject | `TaskContext` |
| --- | --- | --- | --- |
| `on_equip` | `PlayerArmorChangeEvent` | player | player (`Schedulers.run(player)`) |
| `on_hit` | `EntityDamageByEntityEvent` | attacker (projectile → shooter) | attacker entity |
| `on_hurt` | `EntityDamageEvent` | victim | victim entity |
| `on_kill` | `EntityDeathEvent` | killer | killer entity |
| `on_interact` | `PlayerInteractEvent` | player | player |
| `on_block_break` | `BlockBreakEvent` | player | player (block shares the player's region) |
| `tick` | repeating global task, 20-tick period | each online player | each player's (owning) region |
| `on_consume` | `PlayerItemConsumeEvent` | player | player |
| `custom` | `fireCustom(id, ctx)` (no Bukkit event) | caller-provided | caller-provided |

`tick` fans out from a global heartbeat to each online player's own scheduler (Folia-safe), and
short-circuits entirely while no `tick` effect is registered, so it costs nothing in this schema WP.

## Scope note

In this WP the dispatcher starts with **zero** registered effects: no system yet activates a holder's
effects (enchants-on-equip, buffs, perks, set bonuses are later WPs). Item effect bundles are parsed
onto `ItemSpec.effects`, but surfacing them onto the live `ItemDefinition.effects` needs a one-line
change in `ContentRegistrarRpg` (out of this WP's file scope); enchant effects are fully wired because
`EnchantSpec.toEnchantment()` returns them with no registrar change. This WP ships the schema and the
mechanism, not the content.
