# WP-6.2 — Level bands, multipliers and the distance fallback curve

Areas carry a level band; mob stats and loot scale with it. This is the first WP to use RamCore's
region engine (`dev.willram.ramcore.region`) from RamRPG. It builds `LevelBandService`
(`core/regions/LevelBandService.kt`), wires it through the `MobModule` seam WP-1.7b reserved
(never `RamRPG.kt` — B5), and applies it from `EntitySpawnListener` (mob stats, once at spawn) and
`LootListener` (loot, at death).

## `LevelBand`

```kotlin
data class LevelBand(
    val id: ContentId,
    val minLevel: Int,
    val maxLevel: Int,
    val statMultiplier: Double,
    val tierWeights: Map<String, Double> = emptyMap(),
    val lootTableOverride: LootTable? = null,
)
```

`tierWeights` keys are the same tier names `builtin/entities/BuiltinEntities.kt`'s `TIERS` already
uses (`uncommon`/`rare`/`epic`/`legendary`; the implicit remainder is "common"/untiered). `lootTableOverride`
is a RamCore `LootTable` that replaces a mob's own drops while the mob is standing in the band; every
shipped band ships `null` (see "Loot" below).

## The 5 shipped bands (`content/regions/bands.conf`)

One band per `docs/design/0.1-power-curve.md` band, same anchors (player level range and the target Mob
HP/damage-per-hit ranges that document defines):

| Band | id | Levels | `statMultiplier` | `tierWeights` | Region radius (blocks) |
| --- | --- | --- | --- | --- | --- |
| 1 | `ramrpg:band_1` | 1–10 | 1.0 | `{}` | 1000 |
| 2 | `ramrpg:band_2` | 11–25 | 3.0 | `{uncommon: 0.15}` | 2000 |
| 3 | `ramrpg:band_3` | 26–45 | 10.0 | `{uncommon: 0.25, rare: 0.08}` | 3000 |
| 4 | `ramrpg:band_4` | 46–70 | 35.0 | `{uncommon: 0.30, rare: 0.15, epic: 0.05}` | 4000 |
| 5 | `ramrpg:band_5` | 71–100 | 120.0 | `{uncommon: 0.30, rare: 0.20, epic: 0.10, legendary: 0.03}` | 1,000,000 (effectively unbounded) |

**Multiplier ladder.** Chosen as a geometric progression (~3.3× per band) so it tracks
`0.1-power-curve.md`'s own band-to-band Mob HP ratio (60/20≈3.0, 200/60≈3.3, 700/200=3.5, 2500/700≈3.6).
Applied to `builtin/entities/BuiltinEntities.kt`'s lowest baseline mob (zombie, 20 HP), the ladder lands
at 20/60/200/700/2400 HP — at or above each band's documented "Mob HP" lower bound
(`BandStatMultiplierTest` asserts this cross-check against the real packaged `bands.conf`, not a
hand-rolled copy). **These are placeholders, exactly like `0.1-power-curve.md` itself says its own
numbers are** — real tuning is WP-7.4's job, once actual mob content (WP-6.3a/6.3c) and player-side
scaling exist to tune against. A mob with a higher baseline than the 20 HP zombie (e.g. a 100 HP
ravager) will land above a band's documented range even at that band's multiplier; that is expected
variance in the *baseline* profile, not a banding bug — banding scales what a mob already has, it
does not normalize baselines across mob types.

**`tierWeights`.** Also placeholders. Nothing spawns tiered mob variants yet (`builtin/entities/BuiltinEntities.kt`'s
uncommon/rare/epic/legendary overlays are today applied by hand per mob profile registration, not
chosen by band) — WP-6.3a's mob-variant spawning is the intended consumer. This WP ships the data and
one partial consumer: `LootListener` folds `tierWeights.values.sum()` into the RamCore `LootContext.luck`
value it hands to `LootGenerator.generate` (see "Loot" below) — a real, live effect today, even though no
shipped loot pool's `bonusRolls` function currently reads `luck` (the same "wired, not yet consumed by
content" seam WP-2.3a left for five of its seven damage types).

**Region radius / distance-fallback agreement (see below).** The five regions are concentric spheres
centred on `(0, 64, 0)` in the world named `"world"`, with radius `bandIndex × 1000` (band_5's radius is
a very large finite number standing in for "unbounded" — `RegionShapes.sphere` requires a positive
radius). Priority is inverted (band_1 highest, band_5 lowest) so `RegionRuleEngine.regionsAt`'s
highest-priority-first ordering picks the innermost (smallest) containing sphere. This is deliberately
NOT hand-placed geography (no shipped RamRPG map exists) — it is the region-engine machinery proven end
to end with a dataset that reproduces the distance-fallback curve by construction, so an operator can
freely re-shape `bands.conf`'s regions to their own world without needing to also change the fallback
formula (or vice versa) for the two to keep agreeing.

## Resolution: region first, distance fallback second

`LevelBandService.resolve(position, worldSpawn)` is the pure core:

1. `RegionRuleEngine.regionsAt(position)` — every registered `RuleRegion` containing `position`,
   highest priority first (RamCore's own ordering, not reimplemented). The first one whose id names a
   loaded band wins; an unrecognised region id (not a concern for the shipped content, but tested) is
   skipped, not treated as a hard stop.
2. **No region matched** (open world outside every hand-placed region, or a world other than `"world"`
   that owns none of them): distance-from-spawn fallback.

### The fallback curve

Bands are ordered ascending by `minLevel` and treated as concentric horizontal (X/Z; Y ignored) rings of
width `LevelBandService.RING_WIDTH = 1000.0` blocks from the given world's spawn point:

```
index    = floor(distance(position.xz, worldSpawn.xz) / RING_WIDTH)
index    = clamp(index, 0, bandCount - 1)
band     = bandsByLevel[index]
```

Ring 0 is `[0, 1000)` blocks → the lowest-`minLevel` band, ring 1 is `[1000, 2000)`, etc., clamped to
the outermost band past the last ring (never null, never throws, as long as at least one band is
loaded). `distance` is straight-line 2D distance (`sqrt(dx² + dz²)`), not axis-sum — verified directly
by `DistanceFallbackTest`. Y is ignored deliberately: a player standing on a tall tower near spawn should
not be pushed into a harder band by altitude alone.

This is a genuinely **pure** function: `Position.of(x, y, z, worldName: String)` never touches Bukkit
(only `Position.of(Location)`/`.toLocation()` do), so `resolve` and everything it calls
(`RegionShapes`, `RuleRegion.contains`, `RegionRuleEngine.regionsAt`) are exercised directly against the
REAL RamCore region engine in `LevelBandResolutionTest`/`DistanceFallbackTest` — not a fake, and not
merely "the band-selection core with a stubbed region result" (the WP's own documented fallback for a
case that turned out not to apply here).

## Resolve-once, cache-on-entity

Rule 4: `RegionRuleEngine.regionsAt` is cheap but not free, and must never run per-tick or
per-damage-instance. `LevelBandService.resolveAndCache(entity)`:

1. Reads the entity's cached band id from RamCore **entity Metadata** (`dev.willram.ramcore.metadata.Metadata.entities()`,
   an in-memory, UUID-keyed `MetadataMap` — NOT Bukkit's native `Metadatable`/`FixedMetadataValue`, and NOT
   PDC). **Eviction (WP-6.2 review):** the band is stored with a non-transient `put`, which RamCore's own
   housekeeping never reclaims (a non-empty map is never `isEmpty()`), so `MobModule` binds
   `LevelBandService.evict` to `EntityDeathEvent` at `EventPriority.MONITOR` (after the loot read) to clear
   a mob's entry on death. **Residual:** a mob that leaves via chunk-unload without dying is not evicted
   today (no suitable event in this Paper api-version); its entry is tiny (one `ContentId`) and a future
   WP can add an `EntitiesUnloadEvent`/despawn hook if uptime growth ever matters. On a hit, returns the looked-up band with **zero**
   region-engine calls.
2. On a miss, calls the pure `resolve` core once (using the entity's current location and its world's
   spawn location), caches the resolved band's id, and returns it.

**Metadata over PDC, and why.** The WP explicitly asks to pick one mechanism and stay consistent with
WP-6.1a (affixes), which the roadmap plan already earmarks for "entity metadata". RamCore's
`dev.willram.ramcore.metadata` package (`Metadata`/`MetadataKey`/`MetadataMap`) is that mechanism in
this codebase — `RAMRPG_ROADMAP_PROMPT.md` Task 4.1 names it explicitly ("Mob buffs too: `BuffService`
targets `LivingEntity`, stored in RamCore Metadata for non-players"). It is intentionally NOT persisted
to disk (unlike the existing `EntityProfilePdc.DEFENSE`/`DAMAGE` PDC keys `EntitySpawnListener` already
writes for combat's damage pipeline to read): an entity that survives a server restart (loaded from a
saved chunk, so no fresh `EntitySpawnEvent`) simply re-resolves its band the next time
`resolveAndCache` runs for it — one extra `regionsAt` call for that one entity, not a recurring cost,
and not a correctness problem (the band would resolve the same way again from the same location).

**Call sites, and why the cache is genuinely resolve-once:**

- `EntityProfileRegistryImpl.resolve(entity)` calls `levelBandService?.resolveAndCache(entity)` as a
  side effect whenever it resolves a profile for that entity (the "resolve picks the band from spawn
  location" instruction) — this is what actually primes the cache.
- `EntitySpawnListener`'s `EntitySpawnEvent` handler calls `profiles.resolve(living)` FIRST (unchanged
  from before this WP), which — via the point above — already primed the cache. It then reads the
  **same** `LevelBandService` off the registry (downcast to `EntityProfileRegistryImpl`, mirroring the
  pre-existing `mythicResolver` external-hook pattern, since `EntitySpawnListener`'s own construction
  site in `RamRPG.kt` cannot be touched — B5) and calls `resolveAndCache` again to read the value back.
  That second call is a cache hit: one Metadata map lookup, no `regionsAt` call.
- `LootListener`'s `EntityDeathEvent` handler does the same read-back after `profiles.resolve(e.entity)`
  — again a cache hit in the common case (the mob spawned through `EntitySpawnListener` earlier in its
  lifetime). A genuine miss here (no prior spawn event, e.g. a restart-persisted mob) costs one
  `regionsAt` call at death, not per-tick.

So across a mob's entire lifetime, `RegionRuleEngine.regionsAt` runs **at most once** (spawn, or death
as a fallback if spawn never primed it) — never scaling with how long the mob lives or how many times it
is damaged.

## Applying the band

**Stats (`EntitySpawnListener`).** `LevelBandService.scale(value, band)` is a pure helper
(`value * band.statMultiplier`, or `value` unscaled when `band` is null) applied to `RamStats.HEALTH`/
`DEFENSE`/`DAMAGE` from the resolved `EntityProfile.baseStats` before the existing attribute/PDC
application code runs (unchanged from before this WP otherwise). `BandStatMultiplierTest` exercises
`scale` directly, off-server.

**Loot (`LootListener`).** `band?.lootTableOverride ?: profile.lootTable` — a band's override, when
present, fully replaces the mob's own table (every shipped band currently ships `lootTableOverride =
null`, so this is a no-op today; see "shipped bands" above for why). Separately, when the band has any
`tierWeights`, `LootListener` rebuilds its `LootContext` (from `RpgLootContexts.forKill`'s fields, via
the `LootContext` record's own canonical constructor — `RpgLootContexts.kt` is outside this WP's file
set, so its `forKill` helper is reused unmodified rather than extended) with `luck =
tierWeights.values.sum()` instead of the default `0.0`. RamCore's own `LootPool.bonusRolls` mechanism
is the documented consumer of `LootContext.luck` (`docs/API.md`'s own `Instanced Loot` example:
`.bonusRolls(context -> context.luck() > 1.0 ? 1 : 0)`); no shipped RamRPG loot pool uses `bonusRolls`
yet, so this is a live, correctly-wired value with no current observable effect — not a stub.

## Why `bands.conf` bypasses `RpgContentLoader`

`content/regions/bands.conf` is loaded directly by `LevelBandService.fromPackagedResource()` (classpath
read + Configurate HOCON parse, no Bukkit), **not** through `RpgContentLoader`/`ContentModule`'s
`content/<type>/` per-entry pipeline (`RpgContentLoader.KNOWN_TYPES` is unchanged by this WP; `regions`
is not added to it, and `ContentLoader.kt` is untouched). Reasons:

- The shipped set is fixed (5 entries) and this WP does not add an operator-editable
  `content/regions/<slug>.conf` authoring path (no `/rpg reload` support for bands yet) — that is future
  work, not this WP's scope.
- Precedent already exists for shipping a field as HOCON-inert: `EntityProfileSpec`'s own doc comment
  says the exact same thing about `EntityProfile.lootTable` ("stays null here... out of WP-1.5a's
  scope"). `LevelBand.lootTableOverride` follows the same seam deliberately, for the same reason (a
  `LootTable` has no HOCON grammar in this codebase yet).
- `bands.conf`'s `region` blocks are real `RegionSpec`s (`RegionSpec.deserialize`), so the geometry/
  priority/rules half of the format IS the same schema `RpgContentLoader` would use if `regions` were
  wired in later — adding that wiring is additive, not a rewrite.

This is the one deviation from the WP's exhaustive file list worth calling out explicitly: the prompt
allowed touching `ContentLoader.kt` "if the `regions`/bands content type must register a deserializer
there." It was judged unnecessary for the reasons above, so `ContentLoader.kt` was left untouched.

## Wiring: `MobModule`, not `RamRPG.kt`

`MobModule.setup()` resolves the already-constructed `EntityProfileRegistryImpl` singleton from the
`ServiceContext` (`RpgServiceKeys.ENTITY_PROFILES`, downcast — the same instance `RamRPG.kt` registered
in `load()`), builds `LevelBandService.fromPackagedResource()`, binds it (`AutoCloseable`, frees the
private `RegionRuleEngine`'s registry on disable), and sets it on the registry's `levelBandService` var
— the same external-hook pattern the registry already exposes for `mythicResolver`. This is the only
way to reach `EntitySpawnListener`/`LootListener`'s band lookups without editing `RamRPG.kt` (B5):
both listeners are constructed elsewhere (`EntitySpawnListener` in `RamRPG.kt`'s always-on bootstrap
listeners, `LootListener` in `LootModule`) and hold only an `EntityProfileRegistry` reference; since
module `setup()` calls all run during the same `enable()`, before any entity can spawn, `MobModule`
setting the var is guaranteed to happen before either listener's handler ever fires.

`ModuleSeamTest` moved `MobModule` from the seeded-empty set to the populated set (8 populated / 8
seeded-empty, following the exact precedent WP-1.5a set moving `ContentModule` the same way) —
`MobModule.setup()` now resolves a real service and touches Bukkit (RamCore Metadata), so, like every
other populated seam, it is exercised only via construction in that test, never via `setup()`.

## Boundaries respected

- No parallel region/geometry system: shape containment, priority ordering and `RuleRegion`/`RegionSpec`
  come entirely from RamCore.
- `docs/DESIGN.md` is not edited (regenerated at merge) — `DesignSectionCoverageTest` is expected to go
  red on this branch because this file is not yet linked from the index; that is the documented,
  expected state, not a regression.
- Mob definitions/AI (WP-6.3a) and affixes (WP-6.1a) are untouched; `EntitySpawnListener`'s handler
  still ends where band scaling stops, leaving a clean seam for WP-6.1a to add affix application after
  it, in the same handler, without needing to touch this WP's code.
