# WP-3.0 — Command surface consolidation

One canonical Brigadier `/rpg` tree is now the single command surface. `/skills` is a deprecated
aliasing shim for one release. The station-bound subcommands (`upgrade`, `reforge`, `socket`) are
stripped of logic entirely so later Phase-3 station WPs (smithing 3.1b/3.3, enchanting 3.4b) never need
to edit a command file.

Both `/rpg` and `/skills` are owned by one class, `RpgCommand`
(`core/commands/RpgCommand.kt`), registered by `ContentModule.setup()` through Paper's
`LifecycleEvents.COMMANDS` — the same seam WP-1.5c already used for `/rpg validate`/`/rpg reload`, so
`RamRPG.kt` is never touched. `SkillsCommand` (`core/listeners/SkillsCommand.kt`) is kept only as an
inert shell: its constructor is byte-identical to before, and `register()` is now a no-op, so
`RamRPG.kt`'s bootstrap (`skillsCommand = SkillsCommand(...)` at construction, `skillsCommand?.register(commands)`
in `registerCommands`) stays valid without being edited.

## Canonical `/rpg` tree

```
/rpg validate [dir]                          -- ramrpg.command.validate  (unchanged from WP-1.5c)
/rpg reload [--dry-run]                      -- ramrpg.command.reload   (unchanged from WP-1.5c;
                                                  supersedes the old /skills reload)
/rpg stats                                   -- unguarded (old statsCommand)
/rpg stats gui                               -- unguarded (old statsGuiCommand / "statsgui")
/rpg skills [gui]                            -- unguarded (old guiCommand); bare -> gui
/rpg skills inspect                          -- unguarded (old inspectCommand)
/rpg skills ability list                     -- unguarded (old "ability list")
/rpg skills ability toggle <name>            -- unguarded (old "ability toggle")
/rpg quests                                  -- unguarded (old questsCommand)
/rpg quests abandon <id>                     -- unguarded (old "quest abandon")
/rpg perks                                   -- unguarded STUB (lang: ramrpg.rpg.perks.stub);
                                                  no logic until WP-5.1a
/rpg admin give <itemkey> [count] [target] [seed]   -- guarded: ramrpg.admin
/rpg admin level <skill> <n>                        -- guarded: ramrpg.admin
/rpg admin xp <skill> <amount>                      -- guarded: ramrpg.admin
/rpg admin enchant <name> <level>                   -- guarded: ramrpg.admin
/rpg admin reset [target]                           -- guarded: ramrpg.admin
/rpg help                                    -- unguarded, top-level (old helpCommand)
/rpg version                                 -- unguarded, top-level (old versionCommand)
/rpg upgrade [...]                           -- unguarded DEPRECATED STUB (lang: ramrpg.rpg.upgrade.stub)
/rpg reforge [...]                           -- unguarded DEPRECATED STUB (lang: ramrpg.rpg.reforge.stub)
/rpg socket [...]                            -- unguarded DEPRECATED STUB (lang: ramrpg.rpg.socket.stub)
```

Decisions recorded, as asked for by the WP:

- **`/rpg admin` is one guard, not five.** The old tree only guarded `reload`, `reset` and `give`
  individually with `ramrpg.admin` — `level`, `xp` and `enchant` had no guard at all (a pre-existing
  gap). Grouping all five under one `admin` literal with a single `.requires` closes that gap as a
  side effect of the regrouping the WP mandates. `.requires` on a Brigadier parent node gates the whole
  subtree for parsing/dispatch (same mechanism already used for `validate`/`reload`), so no per-leaf
  guard is needed.
- **`help`/`version` are top-level `/rpg` leaves**, not nested under `skills`. The WP left this as a
  free choice; top-level matches where the old `/skills help`/`/skills version` sat relative to the
  rest of the old tree (siblings of `gui`/`stats`/`quests`, not children of any of them).
- **`reforge`/`socket`/`upgrade` carry zero logic.** All four private handlers that used to implement
  them (`reforgeCommand`, `reforgeClearCommand`, `socketCommand`, `socketClearCommand`,
  `upgradeCommand`) are deleted, not moved — nothing under `/rpg` reads `ReforgeRegistry`/`GemRegistry`
  content or `RarityRules.reforgeXpCost`/`socketCap`/`upgradeCap` any more. `RpgCommand` still accepts
  `ReforgeRegistry`/`GemRegistry` in its constructor (mandated by the WP's API-surface list, presumably
  for uniform DI wiring alongside the other 11 game services) but doesn't read them; both parameters
  are individually `@Suppress("unused")` rather than left to warn.
- **`enchant` is NOT a stub.** It is a distinct admin command (apply an enchant to the held item by
  fiat) from the future *enchanting station* (a player-facing crafting flow, WP-3.4). It moves to
  `/rpg admin enchant` with its old logic intact.

## `/skills` deprecation alias

`RpgCommand.buildSkillsAlias()` registers a second, separate `literal("skills")` root (not a Brigadier
`.redirect()`) so every leaf can send the WP-3.0 deprecation message
(`ramrpg.rpg.skills_deprecated`, `"/skills is deprecated; use /{0}"`) naming its specific new `/rpg`
path before doing anything else. A true `.redirect()` was considered (the WP text explicitly allows it)
but rejected: Brigadier's plain `.redirect(target)` doesn't run code of its own, and the modifier form
that could inject a message is built for source-forking (`execute as X run ...`), not warning-then-forward;
building the alias as its own literal tree keeps the warning trivial and explicit at every leaf.

Two behaviors, per the WP's instruction not to forward regrouped/stripped leaves — the exact
classification is `CommandAliasMap.FORWARDED` (a hand-kept set, pinned by
`CommandAliasMappingTest` alongside `OLD_TO_NEW` so the two can't silently drift apart):

- **Leaves that are STILL a live player feature under `/rpg`** — bare `/skills`, `gui`, `help`,
  `version`, `stats`, `quests`, `statsgui`, `inspect`, `quest abandon <key>`, `ability list`,
  `ability toggle <name>` — warn AND forward to the exact same private handler `/rpg`'s equivalent leaf
  calls (e.g. `/skills stats` warns, then runs the same `statsCommand` that `/rpg stats` runs).
  **Post-review fix:** the first cut of this WP only forwarded the six leaves whose top-level *name*
  was unchanged (`stats`, `quests`, bare/`gui`, `help`, `version`) and left `statsgui`, `inspect`,
  `quest abandon`, `ability list` and `ability toggle` as warn-only dead signposts even though none of
  those four features had actually moved or changed — a functional regression during the deprecation
  window. Adversarial review of the initial commit (`f8e47e8`) caught this; those five leaves (six
  counting `quest abandon`) now forward too, with `quest abandon <key>` and `ability toggle <name>`
  wiring their `key`/`name` arguments with the SAME argument name and type the real `/rpg` leaf uses
  (not a greedy catch-all), since `questAbandonCommand`/`abilityToggleCommand` read those arguments by
  name off the shared `CommandContext`.
- **Leaves that were truly stripped, renamed or regrouped** (`reload` — superseded by the diff-based
  `/rpg reload`; `upgrade`, `reforge`, `socket` — station stubs; `reset`, `give`, `level`, `xp`,
  `enchant` — moved under `/rpg admin`) warn ONLY — there is no unchanged behavior left to forward to.
  Old argument shapes (e.g. `give <itemkey> [count] [target] [seed]`) are absorbed by one optional
  greedy-string argument per leaf so the old invocation still *parses* (no confusing Brigadier syntax
  error), it just produces the warning instead of acting. `reload`/`reset`/`give` keep their old
  `ramrpg.admin` guard on the alias (unprivileged senders get the same "unknown command" experience
  they always did — the alias doesn't loosen anything).

The full old->new path mapping is `CommandAliasMap.OLD_TO_NEW`, and the forward/warn-only classification
is `CommandAliasMap.FORWARDED`, both in `RpgCommand.kt` and both asserted as pure data by
`CommandAliasMappingTest` (`src/test/kotlin/dev/willram/ramrpg/CommandAliasMappingTest.kt`) — no
Brigadier dispatch, no Bukkit statics, no live server (same constraint `ValidateResultFormattingTest`
already documents: BLOCKED on WP-RC2's `CommandTestHarness`). `RpgCommand`'s alias-building code looks
up `OLD_TO_NEW` when sending each warning, so the path STRINGS can never drift from what a player is
actually told; `FORWARDED` is hand-kept in sync with which `.executes` blocks actually call a real
handler (there is no live dispatch to derive it from off-server), which is exactly why the test pins its
contents explicitly rather than trusting it not to rot.

|---|---|---|

| `statsgui` | `rpg stats gui` | warn + forward |

| `ability list` | `rpg skills ability list` | warn + forward |

## Permissions

No new permission nodes. `paper-plugin.yml` is unchanged except `ramrpg.admin`'s `description`, updated
to mention `/rpg admin` instead of the old `/skills reload, reset, give` (the node itself, its default,
and `ramrpg.command.admin`/`ramrpg.command.reload`/`ramrpg.command.validate` are untouched).
`PermissionNodeCoverageTest`'s bijection still holds: every `hasPermission("ramrpg.*")` call in source
(`ramrpg.admin` on `/rpg admin` and, unchanged, on the alias's `reload`/`reset`/`give`;
`ramrpg.command.validate`; `ramrpg.command.reload`) has a declared node, and every declared non-umbrella
node is referenced.

## Lang keys added (sorted position in `lang/en_us.json`)

- `ramrpg.rpg.perks.stub` — `"Perks are not available yet"`
- `ramrpg.rpg.reforge.stub` — `"Reforging now happens at a smithing station"`
- `ramrpg.rpg.skills_deprecated` — `"/skills is deprecated; use /{0}"` (one key for every alias leaf;
  the `{0}` argument is the new path from `CommandAliasMap`)
- `ramrpg.rpg.socket.stub` — `"Socket management now happens at a smithing station"`
- `ramrpg.rpg.upgrade.stub` — `"Item upgrades now happen at a smithing station"`

Pre-existing plain `Component.text(...)` strings in the moved handlers (stats/inspect/give/reset/etc.)
were left as-is — this WP's lang-key requirement is scoped to the new strings it introduces (the alias
warning, the perks stub, and the three station stubs), not a retrofit of every string the moved
handlers already used.

## Testing

`CommandAliasMappingTest` is pure data (asserts `CommandAliasMap.OLD_TO_NEW` and `.FORWARDED` directly)
— no Brigadier tree is built or dispatched, matching the constraint already documented on
`ValidateResultFormattingTest` (no `CommandTestHarness` fake exists in RamCore yet for actually
dispatching a Paper Brigadier command off-server). It separately pins: the full path table; that station
stubs map to the stub path, not a moved implementation; that admin leaves land under `rpg admin`; that
player-facing leaves don't; that every new path is well-formed (`rpg ...`); the exact `FORWARDED` set;
and that the leaves which must stay warn-only (station stubs, admin regroups) never sneak into
`FORWARDED`.
