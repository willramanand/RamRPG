# 2.1b — Quality tiers and durability model

WP-2.1b performs the single Phase-2 **instance-schema** bump. It adds four fields to
`api/items/Items.kt`'s `ItemInstanceData` and moves `ItemSchema.CURRENT` from `1` to `2` (this is the
only WP in Phase 2 allowed to touch `ItemSchema` — rule 5):

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `quality` | `Double` | `0.5` (`DEFAULT_QUALITY`) | how good this particular roll of the item is, in `[0.0, 1.0]` |
| `craftedBy` | `UUID?` | `null` | the crafter's UUID; `null` for drops / world-generated items |
| `maxDurability` | `Int` | `500` (`DEFAULT_MAX_DURABILITY`) | this instance's durability ceiling |
| `durability` | `Int` | `= maxDurability` | current durability (full on create) |

This WP lands **fields + defaults + the quality-scales-rolls formula only**. The behaviours that consume
these numbers are explicitly out of scope and owned elsewhere:

- durability **drain** on use + **inert-at-0** — WP-2.2 (see [0.1 durability](0.1-durability.md), decision D2)
- requirement enforcement + lore rendering — WP-2.1c
- repair (the durability sink) — WP-3.3b

## Quality range and how it scales rolls

`quality ∈ [0.0, 1.0]`. It positions a stat roll **deterministically** within the `[min, max]` band the
`ItemDefinition` declares for that stat:

```
qualityScaledRoll(min, max, q) = min + q * (max - min)
```

- `q = 0.0` → `min` (worst roll), `q = 1.0` → `max` (best roll), `q = 0.5` → the midpoint.
- Deterministic: a pure function of `(min, max, q)` with **no RNG** — the same quality always yields the
  same effective roll. `q` is coerced into `[0, 1]`; a fixed range (`min == max`) collapses to that value
  regardless of quality.

**Why this formula (vs. "quality multiplies the rolled amount").** It is literally the same `[min, max]`
line that `ItemInstanceService.rollStats` already samples with `rng.nextDouble()` — quality just supplies
that `[0,1]` position explicitly instead of drawing it randomly. Choosing this over a multiplicative
`effective = rolled × q` keeps quality and the existing seeded-roll determinism on **one axis** rather
than two: a crafted item's quality and a dropped item's seeded roll are the same kind of number (a
position in the band), so a `quality = 1.0` craft and a lucky max-roll drop land in the same place. A
multiplier, by contrast, would let quality push a roll *below its own declared min* (at `q < 1`) or above
its `max` — breaking the band contract `StatRoll(min, max)` is supposed to guarantee. It is pinned by
`QualityScalesRollsTest`.

Where it is applied: `ItemInstanceService.rollStats` uses it when a caller passes
`ItemInstanceInit.quality` (opt-in, non-null) — the rolls are then positioned by quality with no RNG, and
that quality is stored on the instance. When `ItemInstanceInit.quality` is `null` (every current caller —
loot drops via `RpgLootPayloadCodec`, `/skills give`), the historical seeded-RNG roll is untouched and
the instance takes the default `quality = 0.5`. So drops keep their seeded variance today; the crafting WP
(later) will pass a crafter-derived quality to make crafted gear deterministic.

## Durability model (numbers only; drain is WP-2.2)

Per [0.1 durability](0.1-durability.md) (decision D2 = YES), RPG items carry durability as a first-class
instance number, **not** vanilla `Damageable`. This WP carries only the two numbers:

- `maxDurability` — the ceiling. There is **no definition-side durability field yet**, so `create` seeds
  every instance to `DEFAULT_MAX_DURABILITY = 500` (a placeholder tuned in WP-2.2 alongside drain rates,
  in the spirit of the 0.1 power curve).
- `durability` — the current value, defaulting to `maxDurability` (items are created full).

No draining, no inert-at-0, no repair here — those are WP-2.2 / WP-2.1c / WP-3.3b, which will read these
fields. The vanilla `PlayerItemDamageEvent` is already cancelled globally (`DurabilityListener`), so
Minecraft never breaks an RPG item; that listener is untouched by this WP.

### Why no `ItemSpec` / definition-side durability field

`ItemSpec.kt` is **not touched** by this WP. Durability numbers are placeholders until WP-2.2 tunes drain,
`ItemDefinition` carries no durability today, and seeding every instance from one sane constant keeps this
WP to a clean schema bump. When WP-2.2 needs per-item durability ceilings it can add a definition-side
field then; `create` already funnels through `DEFAULT_MAX_DURABILITY`, so that is a one-line change later.

## `craftedBy` semantics

`craftedBy: UUID?` records who crafted the instance, for future "crafted by <player>" lore, crafter
reputation, or bind-on-craft rules. It is `null` for drops and world-generated items. **This WP never sets
it to a non-null value** — the crafting WP wires it when a player crafts an item; here it only exists,
defaults to `null`, and round-trips through the DTO.

## Migration handling (fresh-server / no-migration policy)

RamRPG is in-house and deploys to **fresh servers** — there is no old PDC data to migrate. Per the
standing policy (and confirmed practice: WP-1.2a shipped its `dataVersion` bump without a fixture
migration test), the v1 → v2 bump ships:

- with `ItemSchemaMigrator` a **documented no-op** — there is no V1→V2 migration engine;
- with **no** `ItemSchemaV1toV2MigrationTest` and **no** checked-in v1 fixture.

It works because the new `ItemDto` JSON fields (`q`, `cb`, `mdur`, `dur`) are **nullable**: Gson leaves an
absent field `null` (it does not run Kotlin constructor defaults), so a v1 blob — which omits those keys —
deserializes with them null, and `ItemDto.toDomain()` substitutes the `ItemInstanceData` schema defaults
(`quality → 0.5`, `maxDurability → 500`, `durability → maxDurability`, `craftedBy → null`). A v1 blob
therefore reads back as a sensible v2 instance without any migration step. `ItemDtoTest` asserts this
default-fill (inline JSON, no fixture); `PdcSchemaStabilityTest` asserts the forward (v2→v2) round-trip of
the new fields.
