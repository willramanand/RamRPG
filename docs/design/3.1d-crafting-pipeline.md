# 3.1d — Crafting content pipeline (loading)

WP-3.1d closes the **loading half** of crafting. Before it, every crafting spec (`RecipeSpec`,
`StationSpec`) was pure-tested but **inert at runtime**: `recipes/` and `stations/` were not loadable
content types, no station content existed, and nothing ever reached the (already service-registered)
`RecipeRegistry` / `StationRegistry`, so `StationBlockListener` opened nothing. This WP makes recipes and
stations first-class content types that load from `content/` and register **owner-scoped** so `/rpg
reload` cleans them up. The **runtime seams** (craft-XP trigger, recipe-book opener, capped-upgrade
write, `validateAddSocket`, rarity-scaled costs) are a **separate follow-up WP** — not wired here.

## What loads

| Content type | Directory | Spec | Registered into | Owner |
| --- | --- | --- | --- | --- |
| Recipes | `content/recipes/` | `RecipeSpec` | `RecipeRegistry` | `ramrpg-content` |
| Stations | `content/stations/` | `StationSpec` | `StationRegistry` | `ramrpg-content` |
| Material items | `content/items/materials.conf` | `ItemSpec` | `ItemDefinitionRegistry` | `ramrpg-content` |

`ContentLoader.kt` gains `TYPE_RECIPES` / `TYPE_STATIONS`, both added to `KNOWN_TYPES` (so the dirs are
no longer "unknown content type" errors) and to the `SpecLoader` deserializer chain; `RpgContentLoadResult`
gains typed `recipes` / `stations` lists (included in `definitions()`).

## Station shipped

`content/stations/smithing.conf` — `id = ramrpg:smithing`, `blocks = ["SMITHING_TABLE"]`, `rows = 5`,
`permitted-kinds = [UPGRADE_INPUT, REPAIR, REFORGE, INSERT_GEM, ADD_SOCKET, REMOVE_GEM]`. Right-clicking a
vanilla Smithing Table now opens the RPG smithing bench (via the pre-existing `StationBlockListener`).
No enchanting station ships (enchant recipes arrive in 3.4b).

## Resolution rules (ContentRegistrarRpg)

The registrar is the one place that touches Bukkit. It registers **stations before recipes** (a recipe
validates its station exists) and **items before recipes** (a `new_item`/`transmute` recipe validates its
output item exists). Every failure **aggregates a source-tagged `ValidationError` and is skipped — the
registrar never throws** (matching the existing `buildItem` unknown-material seam).

- **Station** — `blocks` (raw material names) → `BlockMatcher` via `BlockMatchers.ofMaterials(...)`
  (unknown material aggregated); `rows` + `name` → a RamCore `MenuView` via `Menus.menu(name, rows)`
  (rule 1 — reuse RamCore, never hand-roll a menu). An unknown block material or an out-of-range `rows`
  aggregates an error and the station is skipped.
- **Recipe ingredients** — `item` → `Ingredient.Item`; `material` → `Ingredient.MaterialTag` (names →
  `Set<Material>`, unknowns aggregated); `category` → `Ingredient.Category`; `predicate` →
  `Ingredient.Predicate`. Cost / requirements / outcome are already parsed by `RecipeSpec` and pass
  through unchanged.
- **Recipe references validated against LIVE registries** — station registered; `NewItem`/`Transmute`
  output `ItemDefinition` registered; `Reforge` key registered; `InsertGem` gem registered. Any
  unresolved reference aggregates an error and the recipe is skipped (never registered half-resolved).

## How loading actually happens at enable (and stays single-registration)

`ContentModule` loads the operator's `content/` data folder off-thread and registers under one OWNER on
the global thread (Folia-safe). Two facts shaped the wiring:

1. `extractPackagedContent` was **not** wired at enable (the WP-1.5d gap), so packaged confs never
   reached the data folder and never loaded.
2. RamCore's `ContentRegistry.register` **throws on a duplicate id, even across owners**. The 65 builtin
   items are already registered programmatically by `BuiltinItems` (owner `ramrpg-builtin`) and sets by
   `SetModule`, both via `loadPackaged()` over the shared `PACKAGED_CONTENT` list; folding the material
   items into that list would double-register their ids **and** break the parity tests that pin
   `loadPackaged().items` at 65.

So the crafting pack lives in a **separate** `PACKAGED_CRAFTING_CONTENT` list
(`items/materials.conf`, `recipes/*.conf`, `stations/smithing.conf`). At enable, `ContentModule` extracts
**only that list** into the operator's `content/` (skipping any file that already exists, so operator
edits are never clobbered) and then loads the data folder through the normal pipeline — registering
materials + recipes + the station **exactly once** under `ramrpg-content`. The builtin item/set packs are
never extracted through this owner, so no id is registered twice. Result: recipes + stations genuinely
reach the registries at enable, and operators get editable `.conf` files.

## Reload behavior

`ContentModule.applyToRegistries` now unregisters the content OWNER from **eight** registries — the
original six (items, skills, enchants, entities, reforges, gems) plus **recipes** and **stations** — then
re-registers from the freshly loaded pack. So `/rpg reload` removes a deleted recipe/station and re-adds a
changed one, exactly like every other content type. (Stat *definitions* remain the one type reload cannot
remove — unchanged from 1.5c.)

## Known follow-ups (out of scope here)

- **Runtime seams**: craft-XP trigger, recipe-book opener, capped-upgrade write, `validateAddSocket`
  call, rarity-scaled costs — the RUNTIME half, a separate WP.
- **`new_item` at the smithing station**: `content/recipes/materials.conf`'s refine recipes are
  `new_item` outcomes bound to `ramrpg:smithing`, but `NEW_ITEM` is a crafting/transmute-bench kind in
  the 3.1a model, so the smithing station (correctly, per this WP's spec) does not permit it. Those
  recipes load and register, but are `DISALLOWED_OUTCOME` at craft time until a crafting bench ships or
  the pack is re-pointed — a content/runtime follow-up, not a loading defect.
