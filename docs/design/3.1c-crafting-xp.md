# 3.1c — Crafting XP rates (and the recipe book filter)

WP-3.1c ships the recipe book (a filtered recipe list) and the **crafting XP reward**: skill XP granted
on a successful craft. XP flows through the **existing** `XpSource` mechanism (`api/skills`) — a
`CraftXpSource` is an ordinary `XpSource` handed to `SkillService.addXp`, exactly like the mining /
fishing / `skill_xp`-reward grants — so there is no bespoke craft-XP path. This note fixes the numbers:
the XP formula and its per-tier / per-outcome bases.

## The formula

`CraftXp.xpFor(kind, tier, quality, critical)` is pure and deterministic:

```
xp = base(kind) * tierMultiplier(tier) * qualityMultiplier(quality) * (critical ? CRITICAL_MULTIPLIER : 1)

tierMultiplier(tier)       = 1 + TIER_STEP * (max(tier,1) - 1)     // TIER_STEP        = 0.5
qualityMultiplier(quality) = 1 + QUALITY_WEIGHT * clamp(quality,0,1) // QUALITY_WEIGHT  = 0.5
CRITICAL_MULTIPLIER        = 2.0
```

Every factor is monotonic: a higher tier, a higher `quality` roll, or a critical craft each strictly
raises the grant. `SkillService.addXp` then applies its own `multiplier` on top (the XpSource returns the
base amount, the convention every `XpSource` follows). These are placeholders in the spirit of the 0.1
power curve and the 3.1a quality/crit numbers, and will be tuned with crafting content (roadmap 3.2).

### Base XP per outcome kind

`base(kind)` — the XP at tier 1, quality 0, no crit. Producing a brand-new item and upgrading pay the
most; a repair or a gem removal is cheap busywork:

| Outcome kind    | base | Rationale |
|-----------------|------|-----------|
| `UPGRADE_INPUT` | 12   | The headline smithing sink. |
| `NEW_ITEM`      | 10   | Crafting a fresh item from reagents. |
| `ENCHANT`       | 10   | On par with a new item. |
| `TRANSMUTE`     | 8    | Re-shapes an existing item (quality preserved). |
| `REFORGE`       | 8    | Rerolls a modifier. |
| `ADD_SOCKET`    | 8    | Cuts a new slot. |
| `INSERT_GEM`    | 6    | Fills a slot. |
| `REPAIR`        | 4    | Maintenance. |
| `REMOVE_GEM`    | 3    | Trivial undo. |

`DEFAULT_BASE = 6` covers any future kind not yet tabled (defensive; every current kind is listed).

### Per-tier XP (worked)

`tier` is the crafted item's material tier — WP-3.2a's `tier-N` ladder (1 raw ore → 4 mythic). The
formula takes it as a plain number so the model stays pure; the **caller resolves it** from the output
item's definition (the pure calc cannot read the registry). Worked totals for a `NEW_ITEM` (base 10),
quality 0, no crit:

| Tier | tierMultiplier | XP (base 10) |
|------|----------------|--------------|
| 1    | 1.0            | 10.0         |
| 2    | 1.5            | 15.0         |
| 3    | 2.0            | 20.0         |
| 4    | 2.5            | 25.0         |

A masterwork (`quality = 1.0`) tier-4 `NEW_ITEM` critical craft: `10 * 2.5 * 1.5 * 2 = 75.0`.

## Which skill gets the XP

`CraftXpSource.skillFor(recipe)` grants to a `NewItem` recipe's `qualitySkill` — the same skill whose
level drives the 3.1a quality roll, so crafting a cooked item trains Cooking, a potion trains Alchemy, and
so on. Other outcome kinds (upgrade / repair / enchant / reforge / socket) carry no `qualitySkill`; the
caller supplies the skill explicitly (e.g. a station-configured skill), and `forCraft` returns `null` when
none resolves — so a craft never silently grants XP to the wrong skill. One `XpSourceKey`, `ramrpg:craft`,
tags every craft grant (mirroring the single key `SkillXpRewardAction` uses).

## The recipe book filter

`RecipeBookFilter.visible(recipes, query, state)` is the pure predicate the book renders. It filters by
station (`recipe.station`), by the station's permitted outcome kinds, and — when `onlyCraftable` — by met
requirements (`recipe.requirements` via the WP-2.1a `isMet` against a pure `ItemRequirementState`), then
sorts **craftable-first** with a stable key-ordered tiebreak so what the player can make floats to the
top. It is unit-tested off-server (`RecipeBookFilterTest`); the book itself is a RamCore `PaginatedMenu`.

## The trigger gap (open question for the orchestrator)

The pure model, the `CraftXpSource`, and the book filter are the deliverable. **Nothing fires the XP grant
yet.** The craft path (`CraftingServiceImpl.craft`, out of scope) applies inline and emits no
craft-completion event, and the only success site — `StationMenu`'s craft button (also out of scope) —
fires no event a listener could subscribe to. So no seam exists to hang XP off without editing an
out-of-scope file. When one does, the wiring is one line at that success site:

```kotlin
CraftXpSource.forCraft(recipe, success, tier)?.let { skillService.addXp(player, it) }
```

The recipe book likewise has **no opener** yet (a module/command/station-button that resolves the recipe
list via `ctx.service(RECIPE_REGISTRY)` and the player's `ItemRequirementState`, then calls
`RecipeBookMenu.open`). Both wirings are follow-ups for the orchestrator at merge.
