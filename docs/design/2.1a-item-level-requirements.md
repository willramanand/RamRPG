# 2.1a — Item level bands and requirement gates

WP-2.1a adds three **definition-side** fields to `api/items/Items.kt`'s `ItemDefinition`: `itemLevel`,
`requirements`, and `equipSlots`. This is purely the data model + parsing + builtin population — no
enforcement (WP-2.1c enforces requirements and renders their lore) and no instance-schema change
(`ItemInstanceData`/`ItemSchema` are untouched; that is WP-2.1b's job).

## itemLevel

`ItemDefinition.itemLevel: Int` (default `1`) is a planning/lore number — "the player level this item is
meant for" — not a live mechanic on its own. It is deliberately anchored to the
[0.1 power-curve bands](0.1-power-curve.md) so later WPs (loot tables, region scaling, smithing/crafting
outputs) have a consistent number line to place new content against:

| Band | Player level | itemLevel anchor | Rarity anchor (builtins) |
| --- | --- | --- | --- |
| 1 (starter) | 1–10 | 1 | COMMON |
| 2 (early) | 11–25 | 11 | UNCOMMON |
| 3 (mid) | 26–45 | 26 | RARE |
| 4 (late) | 46–70 | 46 | EPIC |
| 4/5 (late-end) | ~60–70 | 60 | LEGENDARY |
| 5 (end) | 71–100 | 85 | MYTHIC |

`BuiltinItems.kt` derives each vanilla-wrapper and custom item's `itemLevel` from its existing `Rarity`
via this table (`itemLevelFor(rarity)`), rather than hand-picking a number per item — the 6 vanilla
material tiers (wood → netherite) already carry a `Rarity` that roughly tracks their in-game power, and
`Rarity` is itself pinned by `RarityRulesTest` (see [0.1 curves and tiers](0.1-curves-and-tiers.md)), so
reusing it keeps `itemLevel` from becoming a second, uncoordinated axis. `EPIC` and `LEGENDARY` get
distinct anchors (46 / 60) even though no current builtin uses `EPIC`, so the table is ready for content
that does. This is a **planning placeholder** like the power curve itself — the real tuning pass is
WP-7.4.

## Requirement forms

`sealed interface ItemRequirement` (in `api/items/Items.kt`) has three forms:

| Form | Fields | Gate |
| --- | --- | --- |
| `SkillLevel` | `skill: SkillKey, level: Int` | the player's level in `skill` is `>= level` |
| `StatThreshold` | `stat: StatKey, min: Double` | the player's current value of `stat` is `>= min` |
| `PerkOwned` | `perk: ContentId` | the player owns the named perk — **STUB**, see below |

Evaluation is `fun ItemRequirement.isMet(state: ItemRequirementState): Boolean`, where
`ItemRequirementState` is a minimal pure interface (`skillLevel(SkillKey): Int`,
`statValue(StatKey): Double`) — deliberately **not** a live `org.bukkit.entity.Player`, so requirement
logic is off-server-testable (`ItemRequirementEvaluationTest`). Adapting a real player's
`SkillService`/`StatService` state onto `ItemRequirementState`, and actually enforcing the gate
(inert-on-unmet + red lore line), is WP-2.1c's job — out of this WP's scope.

### `PerkOwned` stub decision

`PerkKey` and a perk service do not exist yet — [0.1 perk topology (D3)](0.1-perk-topology.md) records
the intended four-tree design, but no perk code has landed (WP-5.1a is still upcoming). Per the WP
contract, `PerkOwned` therefore carries the raw `dev.willram.ramcore.content.ContentId` a content author
names, not a typed `PerkKey` — promoting it to `PerkKey` is WP-5.1a's job once that type exists.

`isMet` treats `PerkOwned` as **fail-closed**: it always evaluates `false` (unmet), regardless of
`state`. This is a deliberate choice, not an oversight:

- A no-op that reported "met" would silently defeat the purpose of gating an item behind a perk — the
  gate would vanish the moment content used it, which is worse than not having the form at all.
- Fail-closed means an item authored with a `PerkOwned` requirement is *definitionally* locked (once
  WP-2.1c wires enforcement) until WP-5.1a ships `PerkService` and replaces this arm's evaluation. That
  is the correct interim behavior for gear that is explicitly meant to be perk-locked.
- `ItemRequirementEvaluationTest` asserts this explicitly (including against a "state that has
  everything") so the stub cannot regress into `true` by accident during WP-5.1a's implementation without
  a test failing first.

`BuiltinItems.kt`'s MYTHIC `dragon_fang` carries a `PerkOwned` requirement (alongside a `SkillLevel`
one) as a definition-time proof that the form parses, holds, and round-trips correctly end to end — not
as a claim that the gate is live today (it is not; WP-2.1c has not shipped yet either).

### HOCON shape (`ItemSpec`, WP-2.1a)

```hocon
item-level = 15
requirements = [
  { type = skill_level, skill = "ramrpg:combat", level = 10 }
  { type = stat_threshold, stat = "ramrpg:strength", min = 20.0 }
  { type = perk_owned, perk = "ramrpg:dragon_slayer" }   # STUB until WP-5.1a
]
equip-slots = ["HAND"]   # optional; omit to use the category -> slot default below
```

`type` is a closed grammar (mirrors `EffectSpec.one`'s `type` dispatch) — an unrecognised value throws
`ContentDeserializeException` naming it, which `SpecLoader` tags with the offending file + path like
every other content error. `ItemSpec` stays pure: `SkillKey`/`StatKey`/`ContentId` are referenced by
type only, and the only `org.bukkit` surface it touches for these three fields is the `EquipmentSlot`
enum (parsed via the existing `SpecNodes.enumList` helper) — no live Bukkit object is constructed here.

**Not yet wired**: exactly like `ItemSpec.effects` after WP-1.5b, `ContentRegistrarRpg.buildItem` does
not yet copy `spec.itemLevel` / `spec.requirements` / `spec.equipSlots` onto the live `ItemDefinition` —
`ContentRegistrarRpg` is outside this WP's file scope (see Non-Negotiable Rule 9). A HOCON item can be
parsed and inspected on the spec today; surfacing it onto the registered `ItemDefinition` is a one-line
registrar change left for the WP that needs it (WP-1.5d, per the roadmap note this WP exists to unblock).

## `equipSlots` and the category → slot default table

`ItemDefinition.equipSlots: Set<EquipmentSlot>` defaults from `categories` via `EquipSlotDefaults`
(`api/items/Items.kt`), computed once at construction time (a Kotlin default-parameter expression
referencing the earlier `categories` parameter) so every existing `ItemDefinition(...)` call site keeps
compiling unchanged while still getting a sensible slot set for free:

| `ItemCategory` | Default `EquipmentSlot` |
| --- | --- |
| `SWORD`, `AXE`, `PICKAXE`, `SHOVEL`, `HOE`, `BOW`, `CROSSBOW`, `TRIDENT`, `MACE`, `FISHING_ROD` | `HAND` |
| `SHIELD` | `OFF_HAND` |
| `HELMET` | `HEAD` |
| `CHESTPLATE`, `ELYTRA` | `CHEST` |
| `LEGGINGS` | `LEGS` |
| `BOOTS` | `FEET` |
| `ENCHANTED_BOOK`, `MISC` | *(none — not directly equippable)* |

An item with multiple categories gets the union of each category's default slot (e.g. a hypothetical
sword/shield hybrid would default to `{HAND, OFF_HAND}`). Passing `equipSlots` explicitly — including an
explicit empty set — overrides the default entirely; `EquipSlotDefaultsTest` covers both the per-category
table and the override case.

## Builtins

`BuiltinItems.kt`'s vanilla-wrapper items (`DEFS`) get `itemLevel` from `itemLevelFor(rarity)` and a
`requirements` list from `requirementsFor(d)`:

- `COMMON` items (wood/stone/iron/gold tools and starter gear) are **ungated** — band-1 starter content
  should never lock a new player out.
- Weapon categories (`SWORD`/`AXE`/`MACE`/`TRIDENT`/`BOW`/`CROSSBOW`) at `UNCOMMON`+ gate on
  `SkillLevel(RamSkills.COMBAT, combatLevelFor(rarity))` — diamond gear (`UNCOMMON`) requires Combat 10,
  netherite (`RARE`) requires Combat 20.
- Armor categories (`HELMET`/`CHESTPLATE`/`LEGGINGS`/`BOOTS`) at `UNCOMMON`+ gate on half that Combat
  level (armor is worn passively; the weapon is the offense-facing gate) — diamond armor requires
  Combat 5, netherite armor requires Combat 10.
- Tools (`PICKAXE`/`SHOVEL`/`HOE`), `FISHING_ROD`, `ELYTRA`, and `ENCHANTED_BOOK` stay ungated —
  utility gear should not lock out progression in a non-combat skill this WP does not own.

The four hand-authored `CUSTOM` items get individually chosen `itemLevel`/`requirements` fitting their
rarity and theme: `rogue_blade` (RARE, Combat 25 + Strength ≥ 20), `warden_husk_chest` (LEGENDARY,
Combat 45 + Health ≥ 150), `dragon_fang` (MYTHIC, Combat 70 + the `PerkOwned` stub above),
`ember_charm` (UNCOMMON, ungated trinket). None of these get an explicit `equipSlots` override — the
category default (`HAND` for swords, `CHEST` for the chestplate, none for the `MISC` charm) is already
correct for all four.

**Note on the WP's own file list**: the roadmap prompt's file-5 description says "the 6 Kotlin builtin
items", carried over from an earlier state of the codebase (the original roadmap's Task 1.5 also cites
"6 items, 2 abilities, 27 mob profiles" as the pre-HOCON baseline). `BuiltinItems.kt` today registers 4
hand-authored `CUSTOM` items plus ~46 vanilla-wrapper `DEFS` entries (all six material tiers × ten
tool/weapon categories, plus armor, bow/crossbow/trident/mace/rod/elytra, and an enchanted book). This
WP applies `itemLevel`/`requirements` to every entry in both lists (not just 6), since leaving most of
the file's items at the bare defaults would not satisfy "give them sensible itemLevel/requirements/
equipSlots" and there is no reason to special-case a subset.
