# 1.5c — Reload semantics and what is not hot-swappable

WP-1.5c adds `/rpg validate [dir]` and `/rpg reload [--dry-run]` over the WP-1.5a/1.5b HOCON content
pipeline (`RpgContentLoader`, `ContentRegistrarRpg`, owner `ramrpg-content`). Both use RamCore's
`reload` package directly (`ContentSnapshot`, `ContentDiff`, `ContentHashing` via `ContentSnapshot.of`)
and RamCore's raw `dev.willram.ramcore.content.ContentLoader` for the diff -- neither hand-rolls parsing
or diffing (rule 1).

> Like 1.5b, this note is NOT linked from `docs/DESIGN.md` on this branch; the orchestrator regenerates
> that index at merge (execution-plan F.3 step 5a), so `DesignSectionCoverageTest` is expected to be red
> on `wp/1.5c` only.

## `/rpg validate [dir]`

Loads `dir` (default: the plugin's `content/` folder) off-thread via
`RpgContentLoader.load(dir, effects)` -- the SAME loader + effect registries the real pipeline uses --
and prints one `file:path: message` line per `ValidationError` (`ContentModule.formatValidationError`;
`ValidationError.describe()` is RamCore's own `[file] path: message` diagnostics form and is
deliberately not reused for this operator-facing contract). **No side effects**: it never touches a
registry, the renderer cache, or the reload diff baseline. Safe to run repeatedly, including against a
directory other than the live `content/` folder, before ever running `/rpg reload`.

## `/rpg reload [--dry-run]`

1. Off-thread (Folia-safe, blocking file I/O): load `content/` twice -- once through RamCore's raw
   `ContentLoader.load` (for the diff) and once through `RpgContentLoader.load` (for the typed specs
   `ContentRegistrarRpg` registers). See "RamCore gap" below for why this is two loads, not one.
2. Back on the global thread (where every RPG registry expects its mutations): build the new
   `ContentSnapshot` and compute `ContentDiff.data(previousSnapshot, newSnapshot, rawResult)`.
3. Unless `--dry-run`: `ContentModule.applyToRegistries` unregisters owner `ramrpg-content` from **every**
   registry this content pack touches -- `items`, `skills`, `enchants`, `entities`, `reforges`, `gems`;
   **all six**, not a subset (see "Known gap" in the WP-1.5a review: the pre-existing `/skills reload`
   path in `RamRPG.kt`, which reloads the older `ramrpg-override` JSON-patch system, only unregisters
   `itemDefs`/`skillRegistry`/`entityProfiles`/`enchantments` -- four of the six owned registries it
   *could* cover. That path is untouched by this WP (different owner, different system); `/rpg reload`'s
   own unregister list is exhaustive against the registries `ContentRegistrarRpg.registerAll` actually
   writes to, so it does not repeat that omission for `ramrpg-content`).
4. Re-registers everything from the new load under `ramrpg-content` via the same `ContentRegistrarRpg`
   every other content path uses (rule 1: one registration entry point, not a parallel one for reload).
5. Invalidates `PacketItemRenderer`'s cache and marks every online player's stats dirty
   (`StatDirtyReason.WORLD_CHANGED`), both on the global thread.
6. Advances the diff baseline to what is now live, so the *next* `/rpg reload` diffs against this state.

`--dry-run` runs steps 1-2 only and reports the same diff; nothing is unregistered, re-registered, or
invalidated, and the baseline does not advance.

### What happens to load/registration errors on a real (non-dry-run) reload

`/rpg reload` does **not** abort when the new load has errors -- it follows the same aggregate-and-continue
philosophy as startup and `/rpg validate`: definitions that failed to parse or deserialize were never in
the typed result to begin with, so `applyToRegistries` unregisters-then-re-registers exactly the
definitions that DID load cleanly, and the command reports every error alongside the applied diff. An
operator who wants to see problems *before* committing should run `/rpg validate` or `/rpg reload
--dry-run` first; `/rpg reload` was intentionally not given a silent-abort-on-error mode, since a content
pack that fails to parse at all (e.g. a directory typo) would otherwise leave the live registries frozen
on a load whose errors could easily go unnoticed in server logs.

## The `StatService` gap: definitions are decided, not forked

**The known gap (WP-1.5a review):** `StatService.registerDefinition(def: StatDefinition)` takes no
`owner` parameter, unlike every other registry's `register(owner, def)`. A HOCON-authored stat definition
therefore cannot be scoped or unregistered by owner. The WP asked for one of: (a) skip stat definitions
entirely on reload (safest), or (b) escalate an upstream RamCore change -- and explicitly forbade forking
a parallel stat registry.

**What was actually possible within this WP's file scope.** `ContentRegistrarRpg.kt` is not in WP-1.5c's
file list (only `core/commands/RpgCommand.kt` and `core/modules/ContentModule.kt` are), so
`ContentRegistrarRpg.registerAll` cannot be changed to skip its `result.stats.forEach { stats
.registerDefinition(...) }` loop for a reload call specifically -- that loop runs unconditionally for
every call, startup or reload alike, because `registerAll` is the one shared registration entry point
every content type goes through (rule 1: reload reuses it rather than forking a second registration
path). So "skip stat definitions on reload" literally cannot be implemented without either forking a
parallel registrar (explicitly forbidden) or modifying a file outside this WP's scope.

**The decision: rely on `registerDefinition`'s upsert semantics, and document the one real gap.**
`StatServiceImpl.registerDefinition` is `definitions[def.key] = def` -- a plain map replace. It never
throws and never duplicates an entry for the same key. Given that:

- **Added and changed stat definitions ARE hot-swappable.** Editing `base`, `color`, `min`, `max`,
  `per-level`, etc. on an existing `stats/*.conf` and running `/rpg reload` takes effect immediately,
  the same as every other content type -- because the upsert IS safe, there is no reason to suppress it.
- **Removed stat definitions are NOT hot-swappable.** `StatService` has no `unregisterOwner`, so deleting
  a `stats/*.conf` file and reloading leaves its last-registered `StatDefinition` live in the registry
  indefinitely (referenced by key, still resolvable, still contributing to snapshots) until the server
  fully restarts and `StatServiceImpl` is constructed fresh from whatever is on disk at boot.
- **This never orphans or double-registers**, satisfying the WP's actual safety requirement: no crash, no
  duplicate entry, no dangling reference to a removed live object (there IS no live "stat definition
  instance" other than the map entry itself). The failure mode is a harmless stale leftover, not a broken
  state, and it is fully recoverable by a restart.

`ContentModule` tracks this precisely: `snapshotTypes` (an RamRPG-owned `ContentId -> type` side table,
since RamCore's `ContentSnapshot` only carries `id -> hash`, not type) lets `/rpg reload` count exactly
how many `ContentDiff.removed()` ids were `stats/` definitions (`ReloadOutcome.statsOrphaned`) and warn
about them by name in the command output (`ramrpg.rpg.reload.stats_orphaned`). Added/changed stat ids are
not flagged, since nothing is wrong with them.

**In-use stat keys** carry the same caveat one level further: even a *restart* only clears a stat
definition, not any `StatModifier`s that already reference its `StatKey` from items/enchants/etc. still
on disk -- removing a stat that other content still points at leaves those modifiers resolving against
whatever default the (now-missing) definition last had cached, which is an authoring error independent of
reload (the same as it would be on a fresh boot). This WP does not add cross-content reference validation
for stat keys; that is a content-authoring concern, not a reload-safety one.

**If RamCore later adds an owner parameter to `StatService.registerDefinition`** (or an equivalent
`unregisterOwner`), `applyToRegistries` gains a seventh `stats.unregisterOwner(owner)` call and stat
removal becomes fully hot-swappable with no other change to this WP's design.

## Not hot-swappable, summarized

| What | Hot-swappable via `/rpg reload`? | Why |
| --- | --- | --- |
| Item/skill/enchant/entity/reforge/gem: added | Yes | `ContentRegistrarRpg.registerAll` under owner `ramrpg-content` |
| Item/skill/enchant/entity/reforge/gem: changed | Yes | unregister owner + re-register (steps 3-4 above) |
| Item/skill/enchant/entity/reforge/gem: removed | Yes | unregister owner drops it; nothing re-registers it |
| Stat definition: added/changed | Yes | `StatService.registerDefinition` upserts by key (safe) |
| Stat definition: removed | **No** | `StatService` has no `unregisterOwner`; needs a restart |
| Schema version (`ItemSchema.CURRENT`, `PlayerRpgData.dataVersion`) | **No** | out of scope by rule 5; reload never touches instance data or its migrations |
| A `StatKey` still referenced by other live content after its definition is removed | **No** (authoring error) | not a reload concern; same failure exists on a fresh boot |

## RamCore gap found

`RpgContentLoadResult` (WP-1.5a, `core/config/ContentLoader.kt`) does not expose the raw
`dev.willram.ramcore.content.ContentLoadResult` it builds internally, only the typed spec lists +
`errors()`. Computing a `ContentDiff` needs the raw `ContentLoadResult` (`ContentSnapshot.of` and
`ContentDiff.data` both take one), so `/rpg reload` and startup each call RamCore's raw `ContentLoader
.load(dir)` a second time, in addition to the call already inside `RpgContentLoader.load`. This is
harmless (small content directories, off-thread, at most once per reload/boot) but is duplicate blocking
I/O. `core/config/ContentLoader.kt` is outside this WP's file list, so it was not changed here; a future
WP could add `RpgContentLoadResult.raw(): ContentLoadResult` to remove the second load.

## Command-dispatch tests: blocked on WP-RC2

Per the WP contract, no `CommandTestHarness` exists yet in `ramcore-test` (M10) to dispatch a Brigadier
command and assert on sender output. `RpgCommand`'s brigadier tree (argument parsing, the `--dry-run`
literal, message formatting through `Component.translatable`) is therefore untested at the dispatch
level; the three required tests instead exercise the pure pieces `RpgCommand` delegates to
(`ContentModule.applyToRegistries`, `ContentModule.formatValidationError`, and RamCore's own
`ContentDiff`/`ContentSnapshot` over real RamRPG content directories). A real command-dispatch test is
BLOCKED on WP-RC2.

## Permission guard: deferred to WP-1.5e

Per the WP-1.5c task contract, permission guards on the `/rpg validate` and `/rpg reload` command nodes
are explicitly WP-1.5e's scope. Both literals are left open (`// TODO(WP-1.5e)` on each in
`RpgCommand.kt`) rather than given an ad hoc `.requires { hasPermission(...) }` check, so the later WP
adds one consistent permission mechanism across every RamRPG command instead of this WP pre-empting it
with a bespoke check that WP-1.5e would then have to reconcile or remove.

## RamCore reload surface not used (and why)

The WP named `ContentReloadService`, `ContentPack`, `TemplateBound` and `LiveObjectRegistry` as
available RamCore surface. This WP uses `ContentSnapshot`/`ContentDiff` (for the diff) and
`ContentRegistry.unregisterOwner` (for the swap) but NOT the higher-level `ContentReloadService`/
`TemplateBound`/`LiveObjectRegistry` machinery, because RamRPG holds no long-lived references to
loaded definitions: every listener/stage resolves its registry entry fresh per event (e.g.
`EntitySpawnListener`, `LootListener` look up by key each time), so an `unregisterOwner` + re-register
cannot orphan a live object — there is nothing holding the old instance to reconcile. If a later WP
introduces cached/bound live objects (e.g. templated encounters), it should revisit `TemplateBound`/
`LiveObjectRegistry` then.
