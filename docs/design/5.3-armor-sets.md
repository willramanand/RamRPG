# 5.3 — Armor sets: set bonus thresholds and shipped sets

> This note is intentionally NOT linked from `docs/DESIGN.md`; the orchestrator regenerates that index
> at merge (execution-plan F.3 step 5a), so `DesignSectionCoverageTest` is expected to be red on the
> `wp/5.3` branch and only this branch. It is the sole expected failure.

WP-5.3 is the "everything is an Effect" thesis canary: a set's bonuses at every member-count threshold
are ordinary `List<Effect>` bundles, consumed by `SetStatProvider` (a `StatProvider`) exactly like every
other item-based bonus (equipment base stats, enchantments, reforge, sockets) already flows through
`StatService`. No bespoke listener hook exists anywhere in this WP.

## The threshold model

`api/sets/Sets.kt`:

```kotlin
data class SetDefinition(
    val key: SetKey,
    val displayName: Component,
    val members: Set<ItemKey>,
    val thresholds: Map<Int, List<Effect>>,
)
```

`thresholds` maps a **member count** to the `Effect`s granted once at least that many of the set's
`members` are equipped, simultaneously, by the same player. Thresholds **stack**: reaching a higher
threshold does not replace a lower one -- every threshold whose count is `<= activeCount` contributes
its effects. Concretely, for a set with thresholds `{2, 4}`:

| Equipped active members | 2-piece bonus | 4-piece bonus |
| --- | --- | --- |
| 0-1 | inactive | inactive |
| 2-3 | **active** | inactive |
| 4 | **active** | **active** |

This is the standard "Hypixel Skyblock-style" stacking convention (each tier is additive, not a
replacement), and it is what `SetThresholdCountTest` asserts: 2/4 equipped activates exactly the 2-piece
bonus, not the 4-piece one; 4/4 activates both.

`SetStatProvider.provideStats` (`core/services/SetStatProvider.kt`) does the counting per recalculation:

1. Reads the wearer's six equip slots (main hand, off hand, helmet, chestplate, leggings, boots) via
   `ItemInstanceService`/`ItemDefinitionRegistry`, exactly like `EquipmentStatProvider` and friends.
2. For each registered `SetDefinition`, counts how many of those (definition, instance) pairs are
   members (`def.key in set.members`) **and** are not inert (see below) -- `equippedSetCount`.
3. For that count, `setStatsFor` unions every satisfied threshold's `StatEffect` entries into
   `StatModifier`s and appends them to the provider's output.

Only `StatEffect` entries within a threshold's effect list are consumed here -- `SetStatProvider` is a
`StatProvider`, so it only ever emits `StatModifier`s. A threshold's list is still typed
`List<Effect>` (not `List<StatEffect>`) to match the roadmap API exactly and to leave room for a future
WP to wire `damage_stage`/`triggered` set effects elsewhere (the same seam WP-1.5b left open for item
effect bundles in general -- see `docs/design/1.5b-effect-schema.md`'s "Scope note"). No special-casing
was added to make non-stat set effects do anything in this WP; they are simply inert data on the
definition until a later WP gives them a consumer, exactly as items' own generic `effects` list already
works today.

## Inert pieces never count (2.1c)

`equippedSetCount` calls the SAME shared check every item-based provider consults --
`ItemDefinition.isInert(instance, state)` (`api/items/Items.kt`, WP-2.1c) -- before counting a piece:

```kotlin
internal fun equippedSetCount(
    equipped: List<Pair<ItemDefinition, ItemInstanceData>>,
    state: ItemRequirementState,
    set: SetDefinition,
): Int = equipped.count { (def, data) -> def.key in set.members && !def.isInert(data, state) }
```

An item whose `requirements` are unmet, or whose `durability` has hit zero, contributes nothing to a
set's active count -- the same way it already contributes nothing to `EquipmentStatProvider`,
`EnchantmentStatProvider`, `ReforgeStatProvider`, or `SocketStatProvider`. This closes the gap
`docs/design/2.1c-inert-items.md`'s "Sets (WP-5.3, future)" section predicted: an under-leveled or
broken piece can never pad a set's member count to unlock a threshold it has not legitimately earned.

The `ItemRequirementState` `SetStatProvider` evaluates against is built by the SAME
`requirementStateFor`/`ItemRequirementServices` (`core/listeners/EquipmentListener.kt`, WP-2.1c) the
other four providers use -- no parallel requirement-evaluation path. Unlike those four (whose
construction call sites are frozen in `RamRPG.kt`, which WP-2.1c could not touch), `SetStatProvider` is
constructed entirely inside `SetModule` -- a brand-new registration site this WP owns -- so `SetModule`
always passes a REAL `ItemRequirementServices`. There is no fail-closed wiring gap for set-member
requirement/inert checks the way there still is for the four WP-2.1c providers pending orchestrator
wiring at merge.

## Counting rides the existing equipment-dirty trigger, not a new listener

`SetStatProvider` is registered into `StatService` like every other provider
(`stats.registerProvider(SetStatProvider(...), SetModule.OWNER)`). `StatServiceImpl.recalculateNow`
re-queries every registered provider on each recalculation; `EquipmentListener` already triggers that
recalculation (`markDirty(..., StatDirtyReason.EQUIPMENT_CHANGED)` followed by `applyAttributes` ->
`StatService.recalculateNow`) on every armor change, hotbar swap, inventory click, item-break, world
change, and join. Because `SetStatProvider.provideStats` is a pure, no-cache computation invoked fresh
on every call (identical to the four WP-2.1c providers), that existing recalculation IS the set-count
refresh -- there is no separate cache to invalidate and no new listener hook was added anywhere in this
WP (rule 2). `EquipmentListener.kt` itself needed no behavioral change; only its KDoc was extended to
record this.

## Effect-only: no special case

Every number a shipped set grants is an ordinary `type = stat` `Effect`, parsed by the SAME
`EffectSpec` parser items and enchants already use (`core/config/specs/EffectSpec.kt`), consumed by an
ordinary `StatProvider`. There is no bespoke `SetBonusEvent`, no direct Bukkit attribute mutation, and
no special-cased branch anywhere in `SetStatProvider`, `SetModule`, or the content loader for "this is a
set bonus" -- a set threshold's `List<Effect>` is handled exactly as generically as an enchant's
`effects(level)` list. This is the whole point of the WP: if a set bonus could not be expressed as an
`Effect`, the correct response was `STATUS: BLOCKED`, not a special case. It never came up -- every
shipped bonus is a flat stat increase.

## Content loading: `sets/` is a first-class content type, registered by `SetModule`

`core/config/ContentLoader.kt` (`RpgContentLoader`) gained `TYPE_SETS = "sets"` in `KNOWN_TYPES`, a
`SetSpec.deserialize` `ContentDeserializer` registration (mirroring `items`/`enchants` exactly), and a
`sets: List<SetSpec>` field on `RpgContentLoadResult`. This makes `content/sets/` a recognized directory
for BOTH the packaged-jar path (`loadPackaged`) and the operator-editable `content/` folder path
(`load(root, effects)`) `ContentModule` already drives for the other six types.

Unlike those six, however, `sets/` specs are **not** registered by `ContentRegistrarRpg` (out of this
WP's file scope) or applied by `ContentModule`'s reload/unregister machinery. `SetModule` -- the seam
WP-1.7b reserved specifically for this WP -- does its own complete, self-contained load: it builds its
own copy of the three effect registries (`BuiltinEffectActions.registerAll`, the same builtin ids
`ContentModule` registers, so both copies agree structurally), calls
`RpgContentLoader.loadPackaged(effectRegistries)` to read the packaged `content/sets/builtin.conf`
classpath resource, and registers each resulting `SetDefinition` into its own `SetRegistryImpl` under
`SetModule.OWNER`. This mirrors `dev.willram.ramrpg.builtin.items.BuiltinItems`'s precedent exactly,
including its Folia rule-4 carve-out: `loadPackaged` is a small, bounded, one-time classpath read done
**synchronously** at this `enable()`-time module-setup bootstrap point, not scheduled async.

`SetRegistry` is intentionally **not** exposed through `RpgServiceKeys`/`ServiceContext` -- nothing
outside `SetModule` needs it this WP, and adding a new service key would require touching
`RpgServiceKeys.kt`, which is outside this WP's file scope and unnecessary for the stated goal.

An operator wanting to add or override sets on their own server can still drop a `.conf` file under
their `content/sets/` data folder; `RpgContentLoader` recognizes the directory (`KNOWN_TYPES`), but
`SetModule` in this WP only reads the packaged jar resource, not the operator data folder path
`ContentModule` drives (that wiring -- and `/rpg reload` diffing for sets -- is left to a future WP,
exactly as `PacketItemRenderer.kt` wiring for live set lore was left open below).

## Shipped sets

Four sets, one per material tier, each themed and drawn entirely from existing shipped armor pieces
(`content/items/builtin.conf`, WP-1.5d) -- no new items were added:

| Set | Tier | Theme | 2-piece | 4-piece |
| --- | --- | --- | --- | --- |
| Netherite Berserker | Netherite | Crit | +8 Crit Chance | +25 Crit Damage, +5 Ferocity |
| Diamond Vanguard | Diamond | Tank | +15 Defense | +10 True Defense, +40 Health |
| Golden Mystic | Golden | Caster | +20 Wisdom | +30 Wisdom (total 50 at 4/4, since thresholds stack), +2 Health Regen |
| Iron Ranger | Iron | Ranged/Agility | +10 Speed | +5 Attack Speed, +10 Speed (total 20 at 4/4) |

Each set's members are the four armor pieces of one material tier (helmet, chestplate, leggings,
boots) -- there is no weapon/tool member in any shipped set, matching how Hypixel-style RPG sets are
conventionally scoped to armor.

## Lore rendering: `LoreSection.SetBonus`

`api/items/Items.kt` adds `LoreSection.SetBonus`, inserted into `LoreTemplate.DEFAULT` right after
`SocketsLine` (grouping it with the other "what this item gives you" numeric blocks: `Stats`,
`ReforgeLine`, `SocketsLine`, `SetBonus` -- before `Description`/`Enchantments`/the requirement/
item-level/durability footer):

```
Stats, ReforgeLine, SocketsLine, SetBonus, Description, Enchantments, Requirements, ItemLevel, Durability, RarityLine
```

It reads a new `LoreContext.setBonus: SetLoreInfo?` field (default `null`):

```kotlin
data class SetLoreInfo(
    val displayName: Component,
    val totalMembers: Int,
    val activeCount: Int,
    val thresholds: Map<Int, List<Effect>>,
)
```

Rendering produces a header line `"<Name> (<active>/<total>)"` (`ramrpg.set.progress`, YELLOW), then one
label line per threshold ascending (`ramrpg.set.threshold`, "N Pieces") colored GREEN when
`count <= activeCount` ("lit") or DARK_GRAY when not ("dimmed"), followed by that threshold's stat lines
(reusing `LoreContext.statNameLookup`/`statFormatLookup`, same as `LoreSection.Stats`) colored to match
the label. `SetLoreRenderTest` covers this at the pure `LoreContext`/`LoreSection` layer with a
hand-built `SetLoreInfo` fixture.

**Not wired: `PacketItemRenderer.kt`.** Exactly like WP-2.1c's `requirementState`/`skillNameLookup`
fields, `LoreContext.setBonus` defaults to `null` so `PacketItemRendererImpl`'s existing `LoreContext(...)`
construction (out of this WP's file scope) keeps compiling unchanged. Real in-game lore therefore does
not yet show a live per-viewer set-bonus block; a future WP (or the orchestrator, if trivial) computes a
`SetLoreInfo` per equipped item per viewer (using `SetRegistry`/`SetStatProvider`'s own counting logic)
and passes it into `PacketItemRendererImpl.renderUncached`'s `LoreContext` construction. The section's
logic, rendering, and active/inactive styling are fully covered by `SetLoreRenderTest` regardless.

## `SourceType` reuse (no api/stats change)

`SetStatProvider`'s emitted `StatModifier`s are sourced as `ModifierSource(SourceType.ITEM, set.key.id)`.
`api/stats/Stats.kt`'s `SourceType` enum has no `SET` member, and that file is out of this WP's file
scope (only `api/sets/Sets.kt` and `api/items/Items.kt` are this WP's api-layer changes -- see the WP's
file-scope rule 7). Adding a new enum constant there would be technically additive and safe (no
exhaustive `when (SourceType)` exists anywhere in the codebase today, confirmed by grep), but it was
deliberately avoided to keep this WP's api footprint to exactly the two files the WP names. `ITEM` is
the closest existing fit -- a set bonus's currency is fundamentally "you have the right items equipped",
the same category `EquipmentStatProvider`'s own base-stat contributions use. A future WP can promote
this to a dedicated `SourceType.SET` if per-source stat breakdown UI ever needs to distinguish "equipment
base stats" from "set bonus stats" precisely.
