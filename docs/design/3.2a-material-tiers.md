# Material tier ladder

**WP-3.2a** ships a 4-tier material progression as pure content: raw ores (tier 1) refine into ingots
(tier 2), which alloy into higher ingots (tiers 3-4). Each step is a recipe that turns tier-N material
into tier-(N+1) material.

The tier-to-tier gate is **item-id based**: every refine recipe consumes the *specific* lower-tier
`ramrpg:` item, not a raw vanilla material. That is what makes the ladder a real progression rather than
a set of vanilla-smelting reskins.

## Tiers and families

| Tier | Family      | Items                        | Item level | Rarity    | Tags                            |
|------|-------------|------------------------------|------------|-----------|---------------------------------|
| 1    | Raw ore     | Copper, Iron, Tin            | 1          | COMMON    | tier-1, ore, metal              |
| 2    | Base ingot  | Copper, Iron, Tin            | 11         | UNCOMMON  | tier-2, ingot, metal            |
| 3    | Alloy       | Bronze, Steel                | 26         | RARE      | tier-3, ingot, metal            |
| 4    | Mythic      | Mithril                      | 60         | LEGENDARY | tier-4, ingot, metal, precious  |

Rarity and item level track the band anchors from
[2.1a](2.1a-item-level-requirements.md) (COMMON=1, UNCOMMON=11, RARE=26, LEGENDARY=60), so a tier's
rarity and item level always agree. Materials are `MISC` items: no `stat-rolls`, no requirements, no
durability and no quality model -- they are stackable commodities that feed later equipment crafts.

## Refining chain

All recipes live in `content/recipes/materials.conf` and bind to `station = "ramrpg:smithing"` (the live
station definition and recipe registration are a later WP; this WP ships only the pure content).

| Recipe                | Tiered input(s) (`type = item`)          | Catalyst (`type = material`) | Output           |
|-----------------------|------------------------------------------|------------------------------|------------------|
| `refine_copper_ore`   | 2x `ramrpg:copper_ore`                    | 1x COAL / CHARCOAL           | `copper_ingot`   |
| `refine_iron_ore`     | 2x `ramrpg:iron_ore`                      | 1x COAL / CHARCOAL           | `iron_ingot`     |
| `refine_tin_ore`      | 2x `ramrpg:tin_ore`                       | 1x COAL / CHARCOAL           | `tin_ingot`      |
| `refine_bronze`       | 3x `ramrpg:copper_ingot`, 1x `ramrpg:tin_ingot` | -                     | `bronze_ingot`   |
| `refine_steel`        | 3x `ramrpg:iron_ingot`                    | 2x COAL / CHARCOAL           | `steel_ingot`    |
| `refine_mithril`      | 2x `ramrpg:steel_ingot`, 1x `ramrpg:bronze_ingot` | 1x ECHO_SHARD        | `mithril_ingot`  |

Every tiered input resolves to a real item defined one tier below the output; every tier above the first
is produced by at least one recipe; the chain is strictly tier-increasing, so there are no gaps and no
cycles. `MaterialTierChainTest` asserts exactly these properties against the shipped files.

Tin ore refines into **tin ingot** (not steel): tier 1 and tier 2 stay in the same family, fixing the
earlier identity mismatch. Steel is a tier-3 alloy carburised from iron; bronze is the copper+tin alloy.

## How the gate actually works

`Ingredient` (WP-3.1a) has no variant that matches an item's RPG `tags`. The only ingredient that keys
off a vanilla material is `Ingredient.MaterialTag`, and it matches a raw `org.bukkit.Material`, not RPG
tags. So the tier gate is expressed with `Ingredient.Item`, which matches a specific `ItemKey`:

- A tiered input (`{ type = item, item = "ramrpg:steel_ingot" }`) matches **only** the RPG item produced
  by the previous tier's recipe. A plain vanilla Diamond, Netherite Scrap, or Copper/Iron Ingot picked up
  in the world carries no `ItemKey`, so it can never satisfy a refine step.
- A catalyst (`{ type = material, materials = ["COAL", "CHARCOAL"] }`) is a vanilla fuel/reagent; it is
  intentionally *not* the tier gate, only a consumable cost.

## The `tags` field is a seam, not a matcher

`ItemSpec` gains an optional `tags: Set<String>` (default empty, so all 65 existing builtin items parse
unchanged -- this is not a schema bump). Each material carries its tier band there, e.g.
`tags = ["tier-2", "ingot", "metal"]`.

**`tags` is parsed but not yet matched.** Nothing consumes it today:

- No `Ingredient` variant matches on tags. The refine ladder gates on item ids, as above -- it does
  **not** accept "any tier-2 metal".
- The live `ItemDefinition` has no `tags` field, so the labels are not surfaced onto any runtime object.

Making tags matchable is a **separate follow-up WP**, out of WP-3.2a's scope: it adds `ItemDefinition.tags`
plus a new `Ingredient.Tag` kind (and the recipe grammar to reference it). Shipping the parsed field now
lets that WP be an additive change rather than a schema break; the tag scheme below is the vocabulary it
will consume.

### Tag scheme

- `tier-N` -- the tier band (1-4). Exactly one per item.
- `ore` -- a raw, minable material (tier 1).
- `ingot` -- a refined material (tiers 2-4).
- `metal` -- every material in this ladder.
- `precious` -- tier 4 only; reserved for future special handling.

## Materials and catalysts

Every base `material` and every catalyst is a real, obtainable `org.bukkit.Material` (verified against
paper-api 26.1.2). Notably this WP does **not** use `DEEP_DARK_BLOCK` (not a real Material) or `BEDROCK`
(not obtainable in survival), both of which appeared in an earlier draft. The tier-4 catalyst is
`ECHO_SHARD`, obtainable from Ancient City loot chests.
