# 2.3a — Damage types, split rules and resistance formula

Fills the `ELEMENTAL_BREAKDOWN` (600) slot documented as *(empty)* in
[0.1 — Stats and the damage pipeline](0.1-stats-and-pipeline.md), and adds a new `RESISTANCES` (1000)
slot just before `ARMOR_MITIGATION` (1100). This WP builds the **stages + types + resistance stats**
only; weapon/source elemental content (actually dealing fire/frost/lightning/arcane/poison damage) is
WP-2.3b's job.

## The 7 damage types

`DamageTypeKey` constants live in `builtin/identity/BuiltinDamageTypes.kt`: `physical`, `fire`, `frost`,
`lightning`, `arcane`, `poison`, `true`. Each has a `ramrpg.damage_type.<type>` lang key
(`BuiltinDamageTypes.displayName`) and a `resistance_<type>` `StatDefinition`
(`BuiltinDamageTypes.resistanceStat`, registered by `BuiltinStats.registerAll`) — 7 + 7 = 14 new lang
keys, inserted in sorted position in `en_us.json`.

`resistance_true` is registered for schema/UI completeness (so the stats GUI and lang file stay
uniform across all 7 types), but `ResistancesStage` never reads it — see "true damage" below.

## Seed rule (`ElementalBreakdownStage`, priority 600)

This is the **one and only** stage that seeds `DamageContext.components`. Per the WP-2.3a spec ("seeds
components from the weapon/source split, default all-physical if none"): no weapon/source split
mechanism exists yet (that's WP-2.3b content), so today the rule is binary —

- damage already tagged `DamageTag.TRUE` upstream (a future true-damage ability/effect) becomes a
  single all-`true` component: `components = {TRUE: finalDamage}`;
- everything else becomes a single all-`physical` component: `components = {PHYSICAL: finalDamage}`.

Either way `components.values.sum() == finalDamage` at the moment this stage runs — the split rule
partitions the total, it never invents or drops damage (`ElementalSplitSumsToTotalTest`). The other 5
types (fire/frost/lightning/arcane/poison) are fully wired end-to-end (key, resistance stat, lang keys)
but no stage produces a non-zero component of those types until WP-2.3b's weapon content exists to
seed them; `ElementalBreakdownStage` is the natural extension point for that later split logic.

`components` is `clear()`-ed at the top of `apply()` defensively, even though nothing today would ever
call it twice on the same context — see "per-chain reset" below for why this can never accumulate.

## Resistance reduction formula (`ResistancesStage`, priority 1000)

This is the **one and only** stage that consumes `DamageContext.components`. For every
`(type, amount)` pair except `true`:

```
resistance = statService.snapshot(victim).get(resistanceStat(type))   // Player victims only
factor     = 1 - resistance / (resistance + 100)
components[type] = amount * factor
```

This is the same `stat/(stat+100)` diminishing-returns curve `ArmorMitigationStage` uses for `defense`
and `TrueDefenseStage` uses for `true_defense` — reused deliberately so all three defensive stats
"feel" the same (100 resistance ⇒ 50% reduction, 200 ⇒ 66.7%, asymptotic to 100%, never negative
damage). After the loop, `finalDamage` is recomputed as `components.values.sum()` so the stage's output
total always matches the sum of its (possibly reduced) components — `ArmorMitigationStage` (1100) then
applies flat armor to that combined total exactly as it did before this WP.

Only a fire resistance reduces the fire component; frost/physical/other components in the same hit are
untouched (`ResistanceReducesOnlyItsTypeTest`). Mob victims have no per-type resistance data source yet
(only the flat `mob_defense` PDC used by `ArmorMitigationStage`), so a non-`Player` victim's components
pass through this stage unreduced — matching the existing precedent of `TrueDefenseStage`, which is also
Player-only for the analogous true-defense stat. Extending mobs to carry per-type resistances is
out of scope here (WP-2.3b / content territory), not a bug in this stage.

## Physical / true handling

- **Physical** is the default component and behaves exactly as damage did before this WP: subject to
  `resistance_physical` here, then to flat armor mitigation at 1100, same as always.
- **True** damage is exempt from resistances by construction: `ResistancesStage`'s loop skips the
  `true` key outright (`TrueDamageIgnoresResistancesTest` proves this holds even when a huge
  `resistance_true` value is present). True damage is *also* exempt from flat armor mitigation, for
  free: `ArmorMitigationStage` already had a pre-existing guard, `if (DamageTag.TRUE in ctx.tags)
  return`, from before this WP. Because `ElementalBreakdownStage` only ever produces a `true` component
  when `DamageTag.TRUE` is already present on the context, that pre-existing guard and the new
  resistance exemption always agree: true damage bypasses both defenses together, not just one.

## Per-chain component reset (up to 8 ferocity chains)

`DamagePipelineImpl.process()` runs the primary `DamageContext` through every stage once, then drains
`ctx.secondaryQueue` for up to 8 ferocity chains (`maxFerocityChain = 8`), calling `runStages` again for
each one. The queue is populated by `FerocityStage`, which for every proc does:

```kotlin
val sec = DamageContext(ctx.attacker, ctx.victim, ctx.cause, ctx.weapon, ctx.baseDamage)
```

— a **brand-new `DamageContext` instance** per chain, whose `components` field is a fresh
`mutableMapOf()` (see `DamageContext`'s property initializer in `api/combat/Combat.kt`). There is no
shared/static component storage anywhere in this design, so each chain's `ElementalBreakdownStage` run
starts from an empty map and seeds it once, independent of the primary hit or any other chain. The
per-chain reset requirement is therefore satisfied by the pipeline's existing per-chain context scoping,
not by any explicit reset code this WP had to add; `ElementalBreakdownStage.apply()` still calls
`ctx.components.clear()` first as a defensive belt-and-braces measure in case a future change ever
re-invokes a stage on the same context.
