# 2.3a — Damage types, split rules and resistance formula

Fills the `ELEMENTAL_BREAKDOWN` (600) slot documented as *(empty)* in
[0.1 — Stats and the damage pipeline](0.1-stats-and-pipeline.md), and adds a new `RESISTANCES` (1000)
slot just before `ARMOR_MITIGATION` (1100). This WP builds the **stages + types + resistance stats**
only; weapon/source elemental content (actually dealing fire/frost/lightning/arcane/poison damage) is
WP-2.3b's job.

## The 7 damage types

`DamageTypeKey` constants live in `builtin/identity/BuiltinDamageTypes.kt`: `physical`, `fire`, `frost`,
`lightning`, `arcane`, `poison`, `true`. Each has a `ramrpg.damage_type.<type>` lang key
(`BuiltinDamageTypes.displayName`) and a `resistance_<type>` `StatDefinition`
(`BuiltinDamageTypes.resistanceStat`, registered by `BuiltinStats.registerAll`) — 7 + 7 = 14 new lang
keys, inserted in sorted position in `en_us.json`.

`resistance_true` is registered for schema/UI completeness (so the stats GUI and lang file stay
uniform across all 7 types), but `ResistancesStage` never reads it — see "true damage" below.

## Seed rule (`ElementalBreakdownStage`, priority 600)

This is the **one and only** stage that seeds `DamageContext.components`. Per the WP-2.3a spec ("seeds
components from the weapon/source split, default all-physical if none"): no weapon/source split
mechanism exists yet (that's WP-2.3b content), so today the rule is binary —

- damage already tagged `DamageTag.TRUE` upstream (a future true-damage ability/effect) becomes a
  single all-`true` component: `components = {TRUE: finalDamage}`;
- everything else becomes a single all-`physical` component: `components = {PHYSICAL: finalDamage}`.

Either way `components.values.sum() == finalDamage` at the moment this stage runs — the split rule
partitions the total, it never invents or drops damage (`ElementalSplitSumsToTotalTest`). The other 5
types (fire/frost/lightning/arcane/poison) are fully wired end-to-end (key, resistance stat, lang keys)
but no stage produces a non-zero component of those types until WP-2.3b's weapon content exists to
seed them; `ElementalBreakdownStage` is the natural extension point for that later split logic.

`components` is `clear()`-ed at the top of `apply()` defensively, even though nothing today would ever
call it twice on the same context — see "per-chain reset" below for why this can never accumulate.

## Resistance reduction formula (`ResistancesStage`, priority 1000)

This is the **one and only** stage that consumes `DamageContext.components`. For every
`(type, amount)` pair except `true`:

```
resistance = statService.snapshot(victim).get(resistanceStat(type))   // Player victims only
factor     = 1 - resistance / (resistance + 100)
components[type] = amount * factor
```

This is the same `stat/(stat+100)` diminishing-returns curve `ArmorMitigationStage` uses for `defense`
and `TrueDefenseStage` uses for `true_defense` — reused deliberately so all three defensive stats
"feel" the same (100 resistance ⇒ 50% reduction, 200 ⇒ 66.7%, asymptotic to 100%, never negative
damage). After the loop, `finalDamage` is recomputed as `components.values.sum()` so the stage's output
total always matches the sum of its (possibly reduced) components — `ArmorMitigationStage` (1100) then
applies flat armor to that combined total exactly as it did before this WP.

Only a fire resistance reduces the fire component; frost/physical/other components in the same hit are
untouched (`ResistanceReducesOnlyItsTypeTest`). Mob victims have no per-type resistance data source yet
(only the flat `mob_defense` PDC used by `ArmorMitigationStage`), so a non-`Player` victim's components
pass through this stage unreduced — matching the existing precedent of `TrueDefenseStage`, which is also
Player-only for the analogous true-defense stat. Extending mobs to carry per-type resistances is
out of scope here (WP-2.3b / content territory), not a bug in this stage.

## Physical / true handling

- **Physical** is the default component and behaves exactly as damage did before this WP: subject to
  `resistance_physical` here, then to flat armor mitigation at 1100, same as always.
- **True** damage is exempt from resistances by construction: `ResistancesStage`'s loop skips the
  `true` key outright (`TrueDamageIgnoresResistancesTest` proves this holds even when a huge
  `resistance_true` value is present). True damage is *also* exempt from flat armor mitigation, for
  free: `ArmorMitigationStage` already had a pre-existing guard, `if (DamageTag.TRUE in ctx.tags)
  return`, from before this WP. Because `ElementalBreakdownStage` only ever produces a `true` component
  when `DamageTag.TRUE` is already present on the context, that pre-existing guard and the new
  resistance exemption always agree: true damage bypasses both defenses together, not just one.

## Per-chain component reset (up to 8 ferocity chains)

`DamagePipelineImpl.process()` runs the primary `DamageContext` through every stage once, then drains
`ctx.secondaryQueue` for up to 8 ferocity chains (`maxFerocityChain = 8`), calling `runStages` again for
each one. The queue is populated by `FerocityStage`, which for every proc does:

```kotlin
val sec = DamageContext(ctx.attacker, ctx.victim, ctx.cause, ctx.weapon, ctx.baseDamage)
```

— a **brand-new `DamageContext` instance** per chain, whose `components` field is a fresh
`mutableMapOf()` (see `DamageContext`'s property initializer in `api/combat/Combat.kt`). There is no
shared/static component storage anywhere in this design, so each chain's `ElementalBreakdownStage` run
starts from an empty map and seeds it once, independent of the primary hit or any other chain. The
per-chain reset requirement is therefore satisfied by the pipeline's existing per-chain context scoping,
not by any explicit reset code this WP had to add; `ElementalBreakdownStage.apply()` still calls
`ctx.components.clear()` first as a defensive belt-and-braces measure in case a future change ever
re-invokes a stage on the same context.

# WP-2.3b append — weapon component splits and elemental content

Fills in the piece WP-2.3a explicitly deferred: "weapon/source elemental content (actually dealing
fire/frost/lightning/arcane/poison damage) is WP-2.3b's job." `ElementalBreakdownStage` now **consumes**
a weapon's declared damage-component split instead of always seeding all-physical, and one builtin
enchant proves an enchant can contribute its own typed component too.

## `damage-split` — HOCON shape and the sum-to-1.0 rule

An item's `.conf` entry may carry a `damage-split` map, parsed by `ItemSpec.deserialize` and copied
through unchanged onto `ItemDefinition.damageSplit: Map<DamageTypeKey, Double>` by
`ContentRegistrarRpg.buildItem`:

```hocon
damage-split { "ramrpg:physical" = 0.6, "ramrpg:fire" = 0.4 }
```

Keys are namespaced `DamageTypeKey` ids (any of the 7 from WP-2.3a); values are the fraction of the
item's damage that lands as that type. **When present, the fractions MUST sum to `1.0` within a
`0.0001` epsilon** (floating-point HOCON-authoring slop) — `ItemSpec`'s `damageSplit(node, id)` helper
sums the parsed map and throws `ContentDeserializeException("damage-split for '$id' must sum to 1.0 but
summed to $total")` when it doesn't, naming both the offending item's id and the actual sum. Like every
other pure-spec validation in this codebase (see `statRolls`' `min > max` check), this exception is
caught by `SpecLoader` and re-surfaced as a source-tagged `ValidationError` (file + path = the item's
own id, since each item is one entry per file) — a bad split never reaches a built `ItemDefinition`; it
aggregates alongside every other content error instead of crashing the load.

`damage-split` is **absent by default** (the HOCON key is optional). Absent parses to an empty map,
which is exactly the same state `ItemDefinition.damageSplit`'s own constructor default (`emptyMap()`)
produces for a Kotlin-constructed definition that never mentions it at all — there is no separate
"unset" sentinel to keep in sync. This is a DEFINITION field (`ItemDefinition`), never an instance field
(`ItemInstanceData`) — durability/quality/enchants/etc. stay exactly where WP-2.1b/2.1c left them; rule 5
of this WP forbids touching the instance schema, and there was no need to.

## `ElementalBreakdownStage` now consumes the split

WP-2.3a's version always did `components[type] = finalDamage` for a single type (physical, or true).
WP-2.3b's version resolves the attacker's weapon first:

```
DamageContext.weapon (ItemStack?)
  -> ItemInstanceService.identify(stack)   -> ItemInstanceData?
  -> ItemDefinitionRegistry.get(identity.key) -> ItemDefinition?
  -> .damageSplit                           -> Map<DamageTypeKey, Double>   (possibly empty)
```

— see `ElementalBreakdownStage.weaponSplit`. Any failure point (no weapon, an unidentified/vanilla
stack, an unregistered definition, or a definition that simply never declared a split) yields an empty
map, and an empty map is treated identically to "no split": the stage falls back to the WP-2.3a
all-physical seeding byte-for-byte. `DamageTag.TRUE` still short-circuits to a single all-`true`
component before weapon resolution ever runs, exactly as before — a true-damage source ignores elemental
typing the same way it ignores resistances and armor.

The actual "split a base amount proportionally" logic is pulled out into a small pure function,
`ElementalBreakdownStage.seed(target, split, base)`, so it can be (and is) unit-tested with a plain
`Map<DamageTypeKey, Double>` + `Double` — no `DamageContext`, no Bukkit, no weapon resolution required.
`apply()` is a thin wrapper: clear `components`, handle `TRUE`, then call `seed` with the resolved split
and the (bonus-adjusted, see below) base damage.

**Resolving a real weapon `ItemStack` needs a live server.** Modern Paper's `ItemStack` constructor calls
`Material.asItemType()` -> `Registry` -> `RegistryAccess`, which throws `IllegalStateException: No
RegistryAccess implementation found` when run off-server (confirmed while writing this WP's tests — the
same reason `RpgItemRewardTest` disables its scheduler before calling `ItemInstanceService.create`). So
the weapon-stack-to-`ItemDefinition.damageSplit` resolution path itself is **not** unit-tested end-to-end
in `ElementalBreakdownWeaponSplitTest`; per this WP's own test-plan fallback, that test class instead
asserts the pure `seed` core directly (no `ItemStack` needed) plus every `apply()` branch that does not
require constructing one (no-weapon default, `TRUE` override, enchant-bonus blending). The full
weapon-stack path is a `SMOKE_TEST.md`-shaped / on-server concern, matching the precedent
`RpgItemRewardTest` already set for `ItemInstanceService.create`.

## An elemental enchant adds a component (`BuiltinEnchants.Flaming`)

Rule 2 of this WP ("effects are the currency... not a bespoke listener") means the enchant has to work
through the existing `Effect`/`DamagePipelineEffect`/`DamageStageHook` mechanism `EnchantDamageStage`
already scans, not a new listener class. But `EnchantDamageStage`'s attacker-side window runs at pipeline
priority `ENCHANT_OFFENSE` (300) — strictly *before* `ElementalBreakdownStage` (600) clears and reseeds
`components` — so a hook cannot write `ctx.components` directly; anything it wrote there would be wiped
one stage later.

The fix reuses `DamageContext.metadata`, the field this type already exposes for exactly this kind of
inter-stage handoff. `Flaming`'s hook (like `Sharpness`/`Power` before it) adds a flat per-level bonus
straight into `ctx.finalDamage`, and *additionally* stashes that same bonus amount into
`ctx.metadata["ramrpg:elemental_bonus"]` as a `Map<DamageTypeKey, Double>` (accumulating if more than one
such enchant hook fires):

```kotlin
ctx.finalDamage += bonus
val bonuses = ctx.metadata.getOrPut(ElementalBreakdownStage.ELEMENTAL_BONUS_METADATA_KEY) { mutableMapOf() }
bonuses[BuiltinDamageTypes.FIRE] = (bonuses[BuiltinDamageTypes.FIRE] ?: 0.0) + bonus
```

`ElementalBreakdownStage.apply()` reads that map back out before clearing/reseeding:

```
bonusTotal = enchantBonuses.values.sum()
base       = finalDamage - bonusTotal        // the weapon-split-governed remainder
seed(components, weaponSplit, base)          // physical/weapon-split portion
components[type] += bonuses[type]            // fold each enchant bonus back in as its own component
```

Because `bonus` was already added into `finalDamage` by the hook, `base + bonusTotal == finalDamage`
always holds, so `components.values.sum() == finalDamage` continues to hold exactly as WP-2.3a's
`ElementalSplitSumsToTotalTest` requires — the enchant's contribution is additive on top of the weapon's
own split, never double-counted or dropped. `Flaming` targets the same `WEAPON_CATS` as `Sharpness`,
`maxLevel = 3`, `+2.0` fire damage per level; its display name is plain `Component.text("Flaming")` (no
translatable key), matching every other builtin enchant's naming convention (`Sharpness`, `Critical`,
`Power`, etc. are all plain text too) — so no new lang key was needed.

## Content: which builtin weapons declare a split

Per the WP's own guidance ("give elemental/themed weapons a damage-split; keep plain weapons absent =
all-physical"), only the thematically-elemental entries in `content/items/builtin.conf` got one; every
plain tiered weapon (wooden/stone/iron/golden/diamond/netherite swords, axes, the bow/crossbow/mace,
etc.) stays absent -> all-physical, unchanged from WP-2.3a:

| Item | Split | Rationale |
| --- | --- | --- |
| `ramrpg:trident` | 50% physical / 50% lightning | vanilla Channeling ties the trident to lightning |
| `ramrpg:rogue_blade` | 75% physical / 25% poison | an assassin's blade |
| `ramrpg:dragon_fang` | 60% physical / 40% fire | a dragon's fang breathes fire |

`BuiltinItemsParityTest`'s frozen-snapshot comparison does not assert `damageSplit` field-for-field (its
`LegacySnapshot` predates this WP and was deliberately not touched — see rule 9's "adjacent breakage:
report, don't fix" and the parity test's own file-scope note), so these three additions did not require
updating that test; it stayed green throughout this WP.

## Reforge components — explicitly out of scope, follow-up

The WP's API note allows "enchants/reforges MAY add components" but scopes only the enchant into this
WP ("do the ENCHANT here; reforge-components can be a documented follow-up if not clean"). Reforges
(`ReforgeDefinition`/`ReforgeStatProvider`) currently only contribute `StatModifier`s, not
`DamagePipelineEffect`s, so wiring a reforge into the same `ELEMENTAL_BONUS_METADATA_KEY` hand-off would
require extending the reforge content schema and its registrar copy-through — out of this WP's file set.
Left as a follow-up for whichever future WP next touches reforges.
