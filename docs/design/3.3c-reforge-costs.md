# Reforge costs

**WP-3.3c** turns reforging into a normal crafting **recipe**. There is no bespoke reforge command or GUI
path any more: a reforge is a [3.1a](3.1a-crafting-model.md) `Recipe` whose outcome is
`RecipeOutcome.Reforge(reforgeKey)`, run at a smithing station like every other craft. The generic craft
engine already applies it -- `RecipeOutcome.plan` collapses `Reforge(key)` to an `OutcomePlan.Modify` that
stamps `ItemInstanceData.reforge`, and `ReforgeStatProvider` reads that field **unchanged**. This WP adds
the reforge **content** (`content/recipes/reforge.conf`), the pure cost/selection helpers
(`core/crafting/ReforgeOutcomes.kt`), and the cost model documented here -- no engine code and no new stat
path.

## Why "reforge as a recipe"

Before this WP the outcome *type* (`RecipeOutcome.Reforge`) shipped in 3.1a, but nothing produced a
reforge except a stubbed command that told players to visit a station
(`ramrpg.rpg.reforge.stub`). WP-3.3c supplies the recipes that make that real. The payoff is that
reforging rides the exact same machinery as upgrade / repair / socket / enchant:

- **One stat path.** A reforge set by a recipe writes `ItemInstanceData.reforge`, and
  `ReforgeStatProvider.reforgeStatsFor` is still the only code that turns that field into stats. A reforge
  applied by a recipe therefore yields byte-identical stats to one applied any other way -- `ReforgeStatProviderTest` pins the builtin reforges' exact output so this can never drift.
- **The pool is data.** The set of reforge recipes *is* the pool of reforges a player can choose. Adding,
  removing, or re-pricing a reforge option is an edit to `reforge.conf`, not a code change.

## The reforge pool (shipped content)

`content/recipes/reforge.conf` ships one recipe per builtin reforge, each reusing the **existing**
`ReforgeKey` id that `BuiltinReforges` already registers -- no parallel keys:

| Recipe            | Reforge id      | Applies to (from `BuiltinReforges`)            |
|-------------------|-----------------|------------------------------------------------|
| `reforge_fierce`  | `ramrpg:fierce` | weapons: +Damage, +Strength                    |
| `reforge_sharp`   | `ramrpg:sharp`  | weapons: +Crit Chance, +Crit Damage            |
| `reforge_heavy`   | `ramrpg:heavy`  | weapons: +Damage / armor: +Defense             |
| `reforge_pure`    | `ramrpg:pure`   | armor: +Health, +Defense                       |
| `reforge_wise`    | `ramrpg:wise`   | armor: +Wisdom                                  |

Each binds to `station = "ramrpg:smithing"` (the same station the [3.2a](3.2a-material-tiers.md) refine
recipes use). The item being reforged is placed in the station's **target** slot (a reforge is a
`requiresTargetItem` outcome), so a recipe's `inputs` list carries only the reagent -- here a single
`AMETHYST_SHARD` catalyst (a plain vanilla `type = material`, not a tier gate). `ReforgeAsRecipeTest`
parses this file straight through `RecipeSpec` and asserts each entry is a well-formed `Reforge` outcome
over a reforge that actually exists.

## Cost model

A reforge charges an **XP-level cost that scales with the target item's rarity**, reusing the existing,
already-tested `RarityRules.reforgeXpCost` ladder as the single source of truth:

| Rarity     | XP levels (`RarityRules.reforgeXpCost`) | Money (`levels * 25`) |
|------------|-----------------------------------------|-----------------------|
| COMMON     | 3                                       | 75                    |
| UNCOMMON   | 6                                       | 150                   |
| RARE       | 10                                      | 250                   |
| EPIC       | 15                                      | 375                   |
| LEGENDARY  | 25                                      | 625                   |
| MYTHIC     | 40                                      | 1000                  |

`ReforgeOutcomes.reforgeCost(rarity)` returns the full `RecipeCost` (money + XP levels) for a rarity;
money is derived from the XP ladder (`ReforgeOutcomes.MONEY_PER_XP_LEVEL = 25.0`) so both track rarity
monotonically from one ladder. Reforge bonuses depend on the item's *category*, not its rarity, so a
reforge recipe is the same for every item -- only the **cost** scales with rarity.

**Static baseline vs. rarity scaling.** A `Recipe.cost` in HOCON is a fixed value: a recipe cannot know
the rarity of the item that will be dropped into the target slot. So `reforge.conf` carries a fixed
baseline (the RARE row: 10 levels / 250 money), and a runtime that wants to charge by the *actual* target
rarity calls `ReforgeOutcomes.reforgeCost(targetRarity)` when it plans the craft. Shipping both keeps the
content authorable today and the rarity-scaled charge a pure, tested function for the wiring WP to adopt
without an api change.

## Seeded selection (random reforge)

The `type = reforge` grammar names one fixed reforge, so the shipped recipes are deterministic single
reforges. For a future **random-reforge** recipe/runtime, `ReforgeOutcomes` provides a pure, deterministic
picker over the pool:

- `ReforgeOutcomes.pool(reforges)` -- every registered reforge key, ordered by id so selection is stable
  regardless of registration order.
- `ReforgeOutcomes.selectReforge(pool, seed)` -- a splitmix64-seeded index into the (sorted, de-duplicated)
  pool; the same `(pool, seed)` always yields the same key, so a preview and the real craft agree.
- `ReforgeOutcomes.rolledOutcome(pool, seed)` -- wraps the selected key as a `RecipeOutcome.Reforge`.

These mirror `QualityRoll`'s determinism (same mixer) and add no api surface: a random-reforge recipe is a
later, additive change, not a schema break.

## What this WP does not touch

- **The crafting engine.** `RecipeOutcome.plan` and `CraftEngine` already apply a `Reforge` outcome via
  the single `OutcomePlan.Modify` arm; no engine branch is added.
- **`api/`.** No key, outcome, or schema changes -- `RecipeOutcome.Reforge`, `ReforgeKey`, and
  `ItemInstanceData.reforge` all shipped earlier (3.1a / 2.1b).
- **`ReforgeStatProvider`'s output.** Its stat contribution is identical to before; the only edits to it
  and `ReforgeRegistryImpl` are KDoc notes recording their role in reforge-as-a-recipe.
