# WP-1.7b — Service graph, module seams and construction order

This note records the dependency-injection shape RamRPG settled on in WP-1.7b: the service dependency
DAG, the order services are constructed and registered, how each subsystem's registration maps to a
`TerminableModule`, and the reserved-empty seams held for named later WPs.

## Why

Before 1.7b, `RamRPG.kt` held ~23 `lateinit` service/UI fields and a `RamRPG.get()` singleton, and
every subsystem registered its listeners inline in `enable()`. That made `RamRPG.kt` a merge magnet.
1.7b removes the field set: services are constructed and registered under `RpgServiceKeys` in `load()`
(WP-1.7a keyed them), collaborators are resolved from the registry or passed by constructor, and each
migrated subsystem registers through its own module. `RamRPG.get()` survives only as a `@Deprecated`
shim for one release. Anything with lifecycle is bound via `bind`/`bindModule`; there is no manual
`shutdown()` in `disable()`.

## Service dependency DAG (18 services)

Edges point from a service to the services its **constructor** requires (RPG services only; RamCore
collaborators such as `PlayerDataService` are not RPG services and carry no edge). Source of truth:
`core/services/RpgServiceGraph.kt`, enforced by `ServiceRegistrationOrderTest`.

```
platform            (none)
player-store        (none)          [FilePlayerStore over RamCore PlayerDataService]
stats               (none)
skill-registry      (none)
skill-service       -> skill-registry, player-store
item-definitions    (none)
item-instances      -> item-definitions
enchantments        (none)
entity-profiles     (none)
abilities           (none)
ability-service     -> abilities, player-store, skill-service
damage-pipeline     (none)
reforges            (none)
gems                (none)
renderer            -> item-definitions, item-instances, stats, enchantments, reforges, gems
economy             (none)
quest-registry      (none)
quests              -> quest-registry, skill-service, economy, player-store
```

The DAG is acyclic. Only four services have edges (skill-service, item-instances, ability-service,
renderer, quests); the rest are leaves.

## Construction / registration order

`RamRPG.load()` constructs and registers services in this order (a valid topological order of the DAG
above — every dependency precedes its dependent). Recorded as `RpgServiceGraph.constructionOrder`:

1. player-store
2. platform
3. stats
4. skill-registry
5. skill-service        (after skill-registry, player-store)
6. item-definitions
7. item-instances       (after item-definitions)
8. enchantments
9. entity-profiles
10. abilities
11. ability-service     (after abilities, player-store, skill-service)
12. damage-pipeline
13. reforges
14. gems
15. renderer            (after item-definitions, item-instances, stats, enchantments, reforges, gems)
16. economy
17. quest-registry
18. quests              (after quest-registry, skill-service, economy, player-store)

Registration must happen in `load()`: RamCore's `SimpleServiceRegistry` rejects `register(...)` once
`loadAll()` runs (which `RamPlugin#onLoad` calls immediately after `load()` returns). None of these
constructors touch the Bukkit runtime, so moving construction to `load()` is safe.

`ServiceRegistrationOrderTest` asserts (off-server): the graph covers exactly the 18 keys; every
dependency is constructed before its dependent; and RamCore's own resolver accepts the declared order
with `dependsOn` edges (for the 16 stub-able keys — `EconomyService`/`QuestService` are concrete
classes `ProxyFakes` cannot stub, and nothing else depends on them).

## Module seams

`enable()` binds exactly `RpgModules.all(this)` — one `bindModule` per element, one seam per subsystem,
each constructed with the plugin's `ServiceContext` and resolving its collaborators from it.
`ModuleSeamTest` asserts the set equals this list with no missing, extra, or duplicate module.

### Six seams populated by 1.7b (migrating existing registrations)

| Module | Owner | Registers |
| --- | --- | --- |
| `LootModule` | `ramrpg-loot` | `LootListener` (from 1.1a/1.1b) |
| `QuestModule` | `ramrpg-quest` | `BuiltinQuests` + `quests.registerObjectives()` + `QuestProgressListener` (from 1.2a); observes skill XP via `SkillServiceImpl.addXpGainListener` |
| `RewardModule` | `ramrpg-reward` | `RewardActionFactories.standard(...)` + the four RPG factories (the N3 takeover of WP-1.2b's direct `RamRPG.kt` registration) |
| `CombatModule` | `ramrpg-combat` | the 12 damage-pipeline stage registrations + `CombatListener` |
| `EconomyModule` | `ramrpg-economy` | anchors the economy seam (`EconomyService` is a `load()`-time service; no enable-time registration exists yet) |
| `UiModule` | `ramrpg-ui` | `ActionBarUi`, `BossBarUi` (bound as `AutoCloseable` + their subscriptions); `BossBarUi.onXpGain` wired via `SkillServiceImpl.addXpGainListener` |

### Ten seams seeded empty, one per named later WP

| Module | Owner | Reserved for |
| --- | --- | --- |
| `ContentModule` | `ramrpg-content` | WP-1.5a (ContentLoader core) |
| `CraftingModule` | `ramrpg-crafting` | WP-3.1b (Station/Recipe API) |
| `SetModule` | `ramrpg-set` | WP-5.3 (armor sets) |
| `BuffModule` | `ramrpg-buff` | WP-4.1a (buff system) |
| `PerkModule` | `ramrpg-perk` | WP-5.1a (perk trees) |
| `MobModule` | `ramrpg-mob` | WP-6.2 (region scaling / custom mobs) |
| `BossModule` | `ramrpg-boss` | WP-6.4a (bosses via encounters) |
| `VendorModule` | `ramrpg-vendor` | WP-7.1 (vendors) |
| `DungeonModule` | `ramrpg-dungeon` | WP-7.2 (dungeons) |
| `ScheduleModule` | `ramrpg-schedule` | WP-7.3 (daily/weekly scheduling) |

Rule: no seam is created without a WP that uses it. `ModuleSeamTest` verifies each seeded-empty seam
registers nothing yet.

## What stays in `RamRPG` as core bootstrap (deliberately not a module)

The plan (execution-plan note N6) modularizes exactly the six subsystems above. The remaining
foundational registration has no dedicated seam because no later WP re-registers it, and the natural
homes (content loading, enchanting station, mob spawn) are reserved-empty seams that must stay empty
until their WP. It therefore stays in `RamRPG.enable()`/`load()`, resolving collaborators from the
service registry (no fields, no singleton), and is bound to the plugin's terminable consumer:

- Content registration: `registerBuiltins()`, `applyContentOverrides()` (future content loading is
  WP-1.5a's `ContentModule`).
- Stat providers: skill / equipment / enchantment / reforge / socket (future providers register in
  their own module: `SetStatProvider` → `SetModule`, etc.).
- Always-on core listeners bound against the plugin: `EquipmentListener`, `XpListener`, `ManaRegen`
  (also `AutoCloseable`), `PacketRenderListener`, `AbilityListener`, `EntitySpawnListener`,
  `FortuneListener`, `NonCombatXpListener`, `EnchantingListener`, `DurabilityListener`,
  `InventoryRefreshListener`.
- `SkillsCommand` construction (command registration is a `RamPlugin` lifecycle concern in
  `registerCommands`, which a module cannot perform); it now receives `QuestService`, `QuestRegistry`
  and a `reloadContent` callback by injection, and calls the free function `applyPlayerAttributes`
  instead of `RamRPG.get().refreshAttributes(...)`.

Because later WPs touch only their listener classes and their own module (never these registration
sites), `RamRPG.kt` remains a file no later WP needs to modify (acceptance B5).

## Decoupling the skill callbacks (design detail)

`SkillServiceImpl` is built in `load()`, but two reactions to skill events used to reach enable-time
objects held as plugin fields. 1.7b removes those fields:

- **Level-up feedback** (title/message/sound/particles, `markDirty`, milestone economy deposit) is a
  constructor `onLevelUp` callback into a private `RamRPG` method that resolves `stats`,
  `skill-registry` and `economy` from the registry, and re-applies attributes through the new free
  function `applyPlayerAttributes(stats, player)` — so it needs no `EquipmentListener` instance.
- **XP-gain reactions** (boss-bar redraw, quest progress) are registered at enable() by `UiModule`
  and `QuestModule` via `SkillServiceImpl.addXpGainListener`, rather than a plugin-held callback. This
  is why the plugin no longer references `BossBarUi` or `QuestService` for XP notifications.
