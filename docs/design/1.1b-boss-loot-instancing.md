# 1.1b — Boss loot instancing and claim policy

Boss drops move from a single ground drop (raced by whoever gets there first) onto RamCore's
instanced loot (`dev.willram.ramcore.loot`): a boss kill registers **one** claimable `LootInstance`
that every contributor can independently claim their own copy of. **Today** the instance is rolled
from its own `LootGenerator` pass, independently of the ground drop this WP leaves in place (see the
"existing ground drop" section) — so the two are separate rolls, not one shared result. Rolling the
table **once** and feeding both paths (or dropping the ground path entirely) is a **WP-6.4** decision,
made once a real claim UI exists. Real bosses (MobDefinition, EncounterDefinition, phases) also land in
**WP-6.4**; this WP wires the hook against the `isBoss` mobs that already exist in `BuiltinEntities`
(warden, wither, ender_dragon,
elder_guardian).

## Instance shape

- **Scope**: `LootInstanceScope.GROUP` — the instance belongs to the kill, not to one player.
- **Claim policy**: `LootClaimPolicy.PER_PLAYER_ONCE` — each claimant UUID may successfully claim
  exactly once; a second claim by the same UUID returns `LootClaimStatus.ALREADY_CLAIMED`. This is
  RamCore's dedup, not reimplemented RPG state (`LootInstance.claim` tracks `claimedBy` internally).
- **Store**: `InstancedLoot.inMemoryStore()`. A persistent store
  (`InstancedLoot.persistentStore(Store<UUID, LootInstanceSnapshot>, LootPayloadCodec)`) is deliberately
  not wired yet: building a file-backed `Store` needs a data-folder path, and no `ServiceKey` currently
  exposes one to `LootModule` without touching `RamRPG.kt` (out of scope here, B5). `RpgLootPayloadCodec`
  is written and unit-tested now so wiring a persistent store later only needs a `Store` instance, not a
  new codec.
- **Expiry**: `BossLootService.DEFAULT_EXPIRY` = 10 minutes from generation
  (`InstancedLoot.expiresAfter(Instant.now(), expiry)`), matching the RamCore `docs/API.md` "Instanced
  Loot" example. An expired instance's `claim()` returns `LootClaimStatus.EXPIRED`.
- **Sweep interval**: `BossLootService.SWEEP_INTERVAL_TICKS` = 1200 ticks (60s), run from
  `LootModule.setup()` via `PlatformScheduler.repeatGlobal` (Folia-safe global repeating task, never a
  raw Bukkit `BukkitRunnable` — rule 4). `sweepExpired(now)` only removes expired entries from the
  store; it never touches a Bukkit object, so it needs no per-player re-dispatch of its own.

## Contributor selection

`BossLootService.onBossDeath(entity, contributors)` takes the eligible player-id set as a parameter
rather than computing it, because RamRPG has no boss-damage/party-contribution tracking yet (`XpListener`
credits only the killer today, the same limitation). `LootListener` currently passes
`listOfNotNull(killer?.uniqueId)` — a boss kill with no killer (fire/void/etc.) registers no instance.

Contribution is still routed through RamCore's `party.PartyContributionTracker` rather than a raw `Set`:
each contributor id is recorded with `tracker.add(id, 1.0)` and the eligible set is read back with
`tracker.eligible(1.0)`, stored as `LootInstance` metadata (`contributors`, a `List<String>` of UUIDs) for
a future claim UI/command to read. `party.PartyManager` is **not** used: RamRPG has no live party
subsystem yet to source real membership from, and building one is out of this WP's scope (see "Open
questions" in the WP report). `claim()` itself does not gate on this metadata — RamCore's
`LootClaimPolicy` is the sole authority on who may claim and how many times; membership/eligibility
enforcement (e.g. only showing a claim prompt to contributors) is a UI/command concern for WP-6.4, not
duplicated here.

## Interaction with the existing ground drop (deviation, recorded)

`LootListener` does **not** replace the ground drop for `isBoss` mobs with the instanced path — it
additionally calls `BossLootService.onBossDeath`. No claim command/GUI exists yet (that is WP-6.4), so
removing the ground drop now would make every warden/wither/ender_dragon/elder_guardian kill award
nothing until WP-6.4 ships. The instanced copy is generated from an independent `LootGenerator` roll
(its own `Random`), registered, and — since nothing can claim it today — simply expires via the sweep
10 minutes later. WP-6.4 decides how the two paths reconcile once a real claim UI exists (open question
for the orchestrator).

## Codec

`RpgLootPayloadCodec` (`dev.willram.ramrpg.core.loot`) implements RamCore's `LootPayloadCodec` and
round-trips exactly the payload WP-1.1a's `RpgLootFunctions.rpgItemReward` produces: an
`RpgItemPayload(item: ItemKey, init: ItemInstanceInit)`. It is a pure Gson codec (`com.google.gson.Gson`,
already a project dependency) with the same compact-key DTO shape
`ItemInstanceServiceImpl.ItemDto` uses to persist `ItemInstanceData` to PDC — no Bukkit types, so it is
unit-tested entirely off-server (`RpgLootPayloadCodecRoundTripTest`). `encode` rejects any payload that
is not an `RpgItemPayload` with `IllegalArgumentException`, matching `LootPayloadCodec.strings()`'s
precedent of failing loudly rather than silently stringifying an unsupported payload.

## Claim messages

`BossLootService.claim` sends the claiming player one of three lang keys based on
`LootClaimResult.status()`, inline, the same way `QuestServiceImpl.complete` sends its completion
message — matching this codebase's convention that every lang key has a live call site:

| `LootClaimStatus` | lang key |
| --- | --- |
| `SUCCESS` | `ramrpg.loot.claimed` |
| `ALREADY_CLAIMED` | `ramrpg.loot.already_claimed` |
| `EXPIRED` | `ramrpg.loot.expired` |
| `NOT_FOUND` | `ramrpg.loot.expired` (reused — the WP calls for three keys, and both statuses mean "this loot is no longer available to you") |
