# 3.3d — Socket slot caps and gem costs

**WP-3.3d** ships the three socket operations as ordinary crafting **recipes** — cut a new socket slot
(`add_socket`), insert a gem (`insert_gem`), remove a gem (`remove_gem`) — plus the two RPG rules the
generic craft engine does not know: a per-item **slot cap** and the **cost** of each operation. No engine
code and no `api/` change: the outcome types, `RecipeOutcome.plan`, the `RecipeSpec` grammar and the
generic `CraftEngine`/`CraftingServiceImpl` all shipped in 3.1a/3.1b and already apply the collapsed
`OutcomePlan.Modify` each of these outcomes produces. This WP adds pure content, a pure helper, and tests.

## One mechanism, three operations

| Operation | Outcome (3.1a) | Pure plan | Recipe (`content/recipes/sockets.conf`) |
| --- | --- | --- | --- |
| Cut a slot | `AddSocket(socketType, count)` | appends `count` empty `SocketData(socketType, gem=null)` | `cut_socket` |
| Insert a gem | `InsertGem(gem, socketIndex)` | sets the gem at an existing slot | `socket_ruby` … `socket_opal` |
| Remove a gem | `RemoveGem(socketIndex)` | clears the gem at an existing slot | `remove_gem` |

All three are `requiresTargetItem` outcomes, so at craft time `inputs[0]` is the player's target item and
the recipe's `inputs` are the reagents (see `CraftingServiceImpl.contextFor`). The target is transformed,
never consumed.

## Slot cap

Socket slots are bounded per item by **rarity**, reusing the existing shared `RarityRules.socketCap`
ladder — there is no parallel cap table:

| Rarity | COMMON | UNCOMMON | RARE | EPIC | LEGENDARY | MYTHIC |
| --- | --- | --- | --- | --- | --- | --- |
| Max sockets | 1 | 2 | 3 | 4 | 5 | 6 |

**The cap is not in the recipe grammar, and `RecipeOutcome.plan` does not enforce it** — `plan` for
`AddSocket` only *appends* `count` slots and will happily exceed any limit. The cap therefore lives in the
pure helper `dev.willram.ramrpg.core.crafting.SocketOutcomes`:

- `slotCap(rarity)` → `RarityRules.socketCap(rarity)`.
- `canAddSockets(currentSlots, count, cap)` → `count > 0 && currentSlots + count <= cap`.
- `validateAddSocket(sockets, count, rarity|cap)` → `SLOT_CAP_EXCEEDED` / `NON_POSITIVE_COUNT` / `null`.

The runtime (a later pipeline WP) calls `SocketOutcomes.validateAddSocket(target.sockets, count,
RarityRules.socketCap(targetRarity))` **before** applying the cut. `SocketCutMaxSlotsTest` proves a cut the
cap forbids is rejected by the helper even though the raw `plan` would append past it — the gate is the
helper's job, not the plan's.

`InsertGem`/`RemoveGem` add two occupancy rules on top of the index-range check `plan` already does:
`validateInsertGem` rejects an already-occupied slot (`SOCKET_OCCUPIED`); `validateRemoveGem` rejects an
empty one (`SOCKET_EMPTY`); both reject an out-of-range index (`INDEX_OUT_OF_RANGE`, mapped to the existing
generic `invalid_target` message).

## Costs

Costs are placeholder numbers (tuned later with crafting content, like the 0.1 power curve). They live as
constants/functions on `SocketOutcomes` and are **mirrored exactly** by the shipped recipes; the WP-3.3d
tests assert the parsed recipe costs equal the helper output, so content and code share one source of
truth.

| Operation | Money | XP levels | Helper |
| --- | --- | --- | --- |
| Cut socket (base, item has 0 slots) | 500 | 3 | `addSocketCost(0)` |
| Cut socket (per already-present slot) | +500 each | 3 | `addSocketCost(existingSlots)` |
| Insert gem | 250 | 0 | `insertGemCost()` |
| Remove gem | 750 | 0 | `removeGemCost()` |

Cutting scales with the slot count so each additional socket on the same item costs more:
`addSocketCost(n) = 500 + 500·n money, 3 XP levels`. A static HOCON recipe cannot know the target's slot
count, so the shipped `cut_socket` encodes the **base** cost (`existingSlots = 0`); the future runtime
substitutes the scaled cost. Gem insertion also consumes the vanilla gem it is cut from as a reagent
(`Recipe.inputs`), which is separate from the money cost.

## Gems reuse existing keys; stats stay on the existing provider

Every `insert_gem` reuses an existing builtin `GemKey` id (`ruby`, `sapphire`, `emerald`, `amethyst`,
`topaz`, `opal` — see `BuiltinGems`), consuming the vanilla gem it is cut from as its reagent
(`REDSTONE`, `LAPIS_LAZULI`, `EMERALD`, `AMETHYST_SHARD`, `GLOWSTONE_DUST`, `QUARTZ`). No parallel gem
key or item is invented.

Stat contribution is **unchanged**: `SocketStatProvider` (via `socketStatsFor`) already emits each set
gem's `GemDefinition.statContribution`, keyed by `ModifierSource(SOCKET, gemKey)`, and consults the shared
`isInert` gate. The socket operations only change *which* gems occupy `ItemInstanceData.sockets`; the stat
derivation is identical. `GemInsertRemoveTest` proves a gem set by an `insert_gem` craft produces
byte-identical modifiers to the same gem set directly on the instance, and that `remove_gem` withdraws
exactly that contribution again — so there is no bespoke socket-crafting stat path.

## Deferred

`recipes/` is not yet a `RpgContentLoader.KNOWN_TYPES` directory, and no live smithing station registers
these recipes yet — wiring `RecipeSpec` into the loader and binding recipes to a station is a later
pipeline WP. The WP-3.3d tests parse `sockets.conf` straight through `RecipeSpec`, exactly as
`MaterialTierChainTest` does for `materials.conf`.
