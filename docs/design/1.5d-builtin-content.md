# 1.5d — Builtin items as content

WP-1.5d moves the builtin item catalogue from hand-written Kotlin (`BuiltinItems.kt`'s `IDef`/`DEFS`/
`CUSTOM` tables, as they stood after WP-2.1a) to `src/main/resources/content/items/builtin.conf`,
proving the WP-1.5a/1.5b/2.1a HOCON content pipeline end to end while keeping a Kotlin-callable
programmatic entry point. The acceptance bar is **parity**: the HOCON-loaded registry must equal the
old Kotlin-built registry field-for-field. `BuiltinItemsParityTest` asserts this against a frozen
snapshot of the pre-WP Kotlin tables (kept only as independent ground truth inside the test, not
derived from any code this WP touches).

## Closing the registrar seam

WP-1.5b and WP-2.1a both left a deliberate gap: `ItemSpec` already parsed `effects`, `item-level`,
`requirements` and `equip-slots`, but `ContentRegistrarRpg.buildItem` never copied them onto the built
`ItemDefinition` (see their design notes — "not yet wired", "one-line registrar change left for the WP
that needs it"). Parity is impossible until that seam closes, and WP-1.5d owns closing it:

```kotlin
return ItemDefinition(
    ...
    effects = spec.effects,
    itemLevel = spec.itemLevel,
    requirements = spec.requirements,
    equipSlots = spec.equipSlots ?: EquipSlotDefaults.forCategories(spec.categories),
)
```

`buildItem` moved from a private `ContentRegistrarRpg` instance method to a public function on its
companion object, because `BuiltinItems.kt` (a different package, no need for the other six registries
a full `ContentRegistrarRpg` instance requires) uses the exact same mapping instead of forking a second
one — this is *the* guarantee that makes the HOCON path and the "programmatic" path structurally
incapable of drifting apart on the item-building step. Every builtin item's `equipSlots` in
`builtin.conf` is omitted (no `equip-slots` key), so all 65 items fall back to the category default —
none of the old Kotlin definitions overrode it either.

## The HOCON root-must-be-an-object wall (and how builtin.conf works around it)

`docs/design/1.5a-content-schema.md` (and RamCore's own `ContentLoader` KDoc) describe "one entry (a
map with an `id`) or a top-level list of entries" as if it applied uniformly to every content file
extension. It does not for `.conf`: Configurate's `HoconConfigurationLoader` is backed by
typesafe-config's `Config` type, which requires an **object** at the document root — a bare top-level
HOCON array is rejected outright:

```
org.spongepowered.configurate.loader.ParsingException: []@(line N, col 0): null
  ConfigException$WrongType: has type LIST rather than object at file root
```

(Verified empirically against this project's exact Configurate/typesafe-config versions before writing
`builtin.conf` — a two-item root array `.conf` file fails to parse with exactly this error. A root-level
list works fine for `.yml`/`.yaml`, per RamCore's own `ContentLoaderTest.loadsSingleAndListEntries`,
because `YamlConfigurationLoader` has no such `Config`-object restriction.) So a single `.conf` file, as
RamCore's loader actually behaves, can hold **at most one entry**. Sixty-five items will not fit as a
bare array in one `.conf` file.

`builtin.conf` therefore is not RamCore's "top-level list" shape at all — it is **one HOCON object whose
top-level keys are per-item slugs** (the slug is arbitrary; only each child's own `id` field matters to
the loader):

```hocon
wooden_sword {
  id = "ramrpg:wooden_sword"
  ...
}
stone_sword {
  id = "ramrpg:stone_sword"
  ...
}
```

`RpgContentLoader.extractPackagedContent` (in `ContentLoader.kt`) parses this packaged object with
Configurate's own loader — never hand-rolled parsing — and **splits** each top-level child back out into
its own real, independently-valid `<type>/<slug>.conf` file (via `HoconConfigurationLoader...save(child)`)
before RamCore's `ContentLoader`/`SpecLoader` ever see it. Both consumers go through this same split:

- **First-run extraction** into an operator's real data folder: each of the 65 items lands as its own
  `content/items/<slug>.conf` file the operator can edit or delete independently (arguably nicer than
  one 65-item monolith), and extraction is per-file idempotent — an existing destination is never
  clobbered, so a deleted or hand-edited item file stays exactly as the operator left it after a restart
  or plugin upgrade.
- **The "parity path"** (`RpgContentLoader.loadPackaged`, used by `BuiltinItems.registerAll` and by
  `BuiltinItemsParityTest`): extracts into a throwaway temp directory, delegates to the ordinary `load`,
  then deletes the temp directory. No parsing/deserialization logic is duplicated between this and the
  real `content/` pipeline — only the packaging/splitting step is new.

This was verified directly (a scratch test parsed a two-item object-of-entries HOCON string via
Configurate's reader-based `source {}` builder, split it into two files with `.save(child)`, then
re-loaded them through the real `RpgContentLoader.load` and checked every field round-tripped) before
committing to the full 65-item file.

## First-run extraction wiring (what's in scope here, what isn't)

WP-1.5d's file list is `BuiltinItems.kt`, `ContentLoader.kt`, `ContentRegistrarRpg.kt`, and the new
`builtin.conf` resource — it deliberately does **not** include `ContentModule.kt`, which owns the real
`content/` directory pipeline wired to the live server (`platform.runAsync { RpgContentLoader.load(...) }`
in its `setup()`). `RpgContentLoader.extractPackagedContent` is fully implemented and unit-tested here,
but nothing in this WP calls it from `ContentModule`'s real startup path — that one-line addition
(`RpgContentLoader.extractPackagedContent(contentDir.toPath())` before the existing `load` call, still
off-thread inside the same `runAsync` block) is left as a follow-up for whichever WP next touches
`ContentModule.kt`, so an operator's real `content/items/` folder gets the 65 individual files on first
server start. Until then, `extractPackagedContent` is exercised only by `loadPackaged`'s temp-directory
path (which IS wired into production today, via `BuiltinItems.registerAll`) and by its own tests.

## `BuiltinItems.kt` as a loader-backed shim

`BuiltinItems.registerAll(reg: ItemDefinitionRegistry)` keeps its exact old signature (rule 7 — no api
break; `RamRPG.registerBuiltins()` calls it unchanged) but now:

1. Calls `RpgContentLoader.loadPackaged()` — extracts `builtin.conf`'s 65 entries into a temp dir, loads
   them through the real `RpgContentLoader.load`, and deletes the temp dir.
2. For each resulting `ItemSpec`, resolves `Material.valueOf(spec.material)` directly (curated, packaged
   content — an unresolvable material here is a packaging bug to fail loudly on, not an authoring
   mistake to aggregate the way `ContentRegistrarRpg.registerAll` does for arbitrary operator content).
3. Builds the `ItemDefinition` via `ContentRegistrarRpg.buildItem` (the same seam described above) and
   registers it under the same `"ramrpg-builtin"` owner the old code used.

This is a small, bounded classpath read + single-file HOCON parse of ~65 entries. It runs synchronously
from `RamRPG.registerBuiltins()` — the exact enable()-time bootstrap point the old in-memory Kotlin
construction ran from — which is the Folia rule 4 carve-out ("at load()/enable() bootstrap where the
existing content load already runs"); this is not a raw Bukkit scheduler and not a new async path, just
the same synchronous bootstrap call it always was, now doing a little classpath I/O instead of building
Kotlin objects in memory.

## Parity guarantee (`BuiltinItemsParityTest`)

`BuiltinItemsParityTest` embeds `LegacySnapshot`, a frozen copy of the WP-2.1a `BuiltinItems.kt` (the
`IDef`/`DEFS`/`CUSTOM` tables and the exact `itemLevelFor`/`combatLevelFor`/`requirementsFor`/
`weaponRolls`/`armorRolls` derivations `registerAll` used to run), kept deliberately independent of the
production code so a future regression in `builtin.conf` or the loader/registrar wiring fails the test
instead of silently drifting into a tautology. It then calls the REAL `BuiltinItems.registerAll` against
a fake `ItemDefinitionRegistry` and asserts, per item key (all 65): `key`, `displayName`, `material`,
`rarity`, `categories`, `baseStats` (as a set — map iteration order is not a promised part of this
contract), `effects`, `maxStack`, `customModelData`, `allowVanillaWrapper`, `description`, `statRolls`
(as a set), `itemLevel`, `requirements` (as a set), and `equipSlots` all match. A second test
(`packaged content loads with no errors and every entry resolves its material`) is a narrower sanity
check directly against `RpgContentLoader.loadPackaged()`.

One assumption worth recording since it is not obvious: the legacy Kotlin displayName was built with
`Component.text(name)` (plain, no MiniMessage parsing), while the HOCON path builds it with
`MiniMessage.miniMessage().deserialize(name)` (`ItemSpec`'s `SpecNodes.componentOr`). For every builtin
item's plain-text name (no MiniMessage tags), both constructions produce an equal `Component` — verified
by the parity test actually passing, not merely assumed. If a future builtin item's name needs
MiniMessage formatting, this equality still holds as long as the Kotlin-side comparison is updated to
match (not a concern for WP-1.5d's ungated plain names).

## No round-trip gaps found

Every field WP-1.5b (`effects`) and WP-2.1a (`itemLevel`, `requirements`, `equipSlots`) added round-trips
cleanly once the registrar seam above is closed; no schema gap needed reporting as BLOCKED for this WP.
`effects` is trivially empty on both sides (no builtin item declares an `effects` bundle), so this WP
does not exercise `EffectSpec` parsing beyond confirming it stays a no-op when absent.
