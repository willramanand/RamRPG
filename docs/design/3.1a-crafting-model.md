# 3.1a — Station and recipe model; quality roll formula; critical-craft chance

WP-3.1a designs the **whole** `api/crafting` surface up front so smithing (upgrade / repair / reforge /
socket), enchanting, and generic crafting are all just **recipes with different outcomes** — there is no
bespoke per-station code path to write later. It ships the API + two pure HOCON specs + pure tests only;
every runtime (`CraftingServiceImpl`, `RecipeRegistryImpl`, the station `MenuView`, the spec registrar)
is WP-3.1b, and three outcome runtimes are deferred further still (see the deferral table below).

## One mechanism, three stations

| Concept | Type | What it is |
| --- | --- | --- |
| Station | `Station(key, displayName, blockMatcher, menuLayout, permittedKinds)` | A vanilla block (`blockMatcher`) that opens a RamCore menu (`menuLayout`), restricted to the `RecipeOutcomeKind`s in `permittedKinds`. |
| Recipe | `Recipe(key, station, inputs, requirements, cost, outcome)` | `inputs` (ingredients) + `cost` → `outcome`, gated by `requirements`. |
| Ingredient | `sealed Ingredient { Item, MaterialTag, Category, Predicate }` | One required input, each with a `count` and a **pure** `matches(IngredientCandidate)`. |
| RecipeOutcome | `sealed RecipeOutcome { NewItem, UpgradeInput, Repair, Enchant, Reforge, InsertGem, AddSocket, RemoveGem, Transmute }` | What a craft produces — the ONLY thing that differs between stations. |
| QualityRoll | `QualityRoll(skill, seed): Double` | Deterministic craft-quality in `[0,1]`, feeding WP-2.1b. |

A smithing station is
`permittedKinds = {UPGRADE_INPUT, REPAIR, REFORGE, INSERT_GEM, ADD_SOCKET, REMOVE_GEM}`; an enchanting
station is `{ENCHANT}`; a crafting/transmute bench is `{NEW_ITEM, TRANSMUTE}`. The same `Recipe`/
`CraftingService`/`CraftPlanner` machinery drives all three. **Reforging stops being a special path**: it
is a `Recipe` whose outcome is `RecipeOutcome.Reforge(reforgeKey)` with a reagent `cost`, exactly like
every other recipe — the whole point of shipping the Reforge and socket types now (roadmap 3.3's mandate).

### The full socket surface ships now (no api change for WP-3.3d)

Socketing is **three** distinct outcome arms (and three `RecipeOutcomeKind`s, so a station can permit
some and not others), covering everything WP-3.3d's runtime needs:

| Arm | Kind | Pure plan | HOCON |
| --- | --- | --- | --- |
| `AddSocket(socketType, count)` | `ADD_SOCKET` | appends `count` empty `SocketData(socketType, gem=null)` to the target | `{ type = add_socket, socket-type = "ns:generic", count = 1 }` |
| `InsertGem(gem, socketIndex)` | `INSERT_GEM` | sets the gem at an existing socket index (out-of-range → `INVALID_TARGET`) | `{ type = insert_gem, gem = "ns:ruby", index = 0 }` |
| `RemoveGem(socketIndex)` | `REMOVE_GEM` | clears the gem at an existing socket index (out-of-range → `INVALID_TARGET`) | `{ type = remove_gem, index = 0 }` |

`InsertGem` is the former single `Socket` arm, renamed for clarity; `AddSocket`/`RemoveGem` are new. All
reuse the existing `SocketData`/`GemKey` — no parallel keys. `SocketData.key` is a slot/type id (not used
by `SocketStatProvider` today, which reads only the gem), so `AddSocket` carries the author-named
`socketType` to stamp onto the cut slots.

### Why these are the right seams

- **Ingredient matching is pure and off-server.** `Ingredient.matches` runs against a pure
  `IngredientCandidate` (material, count, optional RPG key / categories / quality / upgrade level), so it
  is unit-tested with no server. `MaterialTag` is the one reason `api/crafting` imports
  `org.bukkit.Material` — matching a raw vanilla stack has nothing else to go on; it is genuinely
  unavoidable there and used nowhere else in the pure surface. `Predicate` is **structured** (optional
  `itemKey` / `category` / `minQuality` / `minUpgradeLevel`), not a lambda, so it stays HOCON-loadable and
  testable; it is fail-closed when an instance field it needs is unknown.
- **Requirements are reused, not forked.** `Recipe.requirements` is the existing WP-2.1a
  `sealed ItemRequirement` (SkillLevel / StatThreshold / PerkOwned), evaluated with the same `isMet`. No
  new requirement type exists.
- **Cost reuses the economy shape.** RamCore's economy is a per-`UUID` `double` balance
  (`dev.willram.ramcore.economy.Economy`) with no reusable "cost" value object, so `RecipeCost(money,
  experienceLevels)` is the minimal local data type. `money` is charged through that economy by WP-3.1b;
  `experienceLevels` is the vanilla XP-level cost enchanting uses (roadmap 3.4). Reagents are
  `Recipe.inputs`, not cost; skill XP *granted* on a craft is a reward (`XpSource`), also not modelled
  here.
- **Keys are reused.** `RecipeOutcome.Reforge` holds the existing `ReforgeKey` (Items.kt), `Socket` holds
  the existing `GemKey` (Sockets.kt) and writes into the existing `SocketData` list, `Enchant` holds the
  existing `EnchantmentKey`. No parallel keys are invented.

### Spec / registrar seam (spec is pure, registrar resolves on the server)

`StationSpec` and `RecipeSpec` are pure HOCON specs like every other spec. Following the `ItemSpec`
precedent (which holds `material` as a raw `String`), anything Bukkit stays a raw string in the spec and
WP-3.1b's registrar resolves it on the server:

- `StationSpec.blockMaterials` (raw names) → a `BlockMatcher` via `BlockMatchers.ofMaterials(...)`, and
  `rows` + `name` → a RamCore `MenuView` via `Menus.menu(name, rows)`. Because a live `Station` needs a
  server to build both, `StationSpec` has **no** `toDefinition()` (mirroring `ItemSpec`).
- `RecipeSpec` builds everything pure directly (the `RecipeCost`, the `ItemRequirement` gates, the
  `RecipeOutcome` — all key-based), and holds only the ingredient list as raw `RecipeIngredientSpec`
  (material names as strings), because `Ingredient.MaterialTag` carries `Material`. WP-3.1b's registrar
  resolves those into live `Ingredient`s (raising "unknown material" there, the same seam `ItemSpec` uses).
- Neither spec needs `EffectSpec.Registries`: a recipe/station references content only by typed key
  (ContentId), resolved structurally, so nothing needs registry lookup at parse time (unlike an
  item's/enchant's `effects` bundle).

### RamCore reuse and the one gap

- **Menu:** `Station.menuLayout` is RamCore's `MenuView`; `CraftingService.open` returns RamCore's
  `MenuSession` — never a RamRPG menu type.
- **Economy / HOCON:** RamCore `Economy` (money) and the RamCore `ContentLoader`/`SpecLoader` + Configurate
  HOCON pipeline (via the existing `RpgContentLoader`) are reused unchanged.
- **Block matcher gap:** RamCore ships **no** block-matcher concept. Rather than fork a new one, `Station`
  reuses RamRPG's own **existing** `dev.willram.ramrpg.api.effects.BlockMatcher` (already used for
  `OnBlockBreak` triggers) — reusing an existing RamRPG concept, not inventing a parallel one. If a
  general block-matcher ever lands in RamCore, `Station.blockMatcher` should migrate to it.

## Quality roll formula (exact math)

`QualityRoll(skill, seed)` is pure and deterministic and returns a `Double` in `[0,1]`:

```
frac    = clamp(skill / SKILL_CAP, 0, 1)        // SKILL_CAP = 100
u       = splitmix64(seed) -> [0,1)             // deterministic uniform from the craft seed
quality = SKILL_WEIGHT*frac + (1 - SKILL_WEIGHT)*u        // SKILL_WEIGHT = 0.5
```

- **Deterministic:** `u` is a splitmix64 finalizer of the 64-bit `seed` mapped to `[0,1)` (top 53 bits /
  2^53). Same `(skill, seed)` → identical `quality`; different seeds diverge (splitmix64 is a bijection
  that spreads inputs well).
- **Skill sets the floor of a half-width window.** With `SKILL_WEIGHT = 0.5`: at `skill = 0`,
  `quality ∈ [0.0, 0.5]`; at `skill = SKILL_CAP`, `quality ∈ [0.5, 1.0]`. Expected quality is
  `0.5*frac + 0.25`, i.e. `0.25` at skill 0 rising to `0.75` at cap — **monotonic in skill**, and for a
  *fixed seed* the exact value strictly increases with skill (coefficient `0.5 > 0`). Randomness keeps two
  crafts of the same item at the same skill different.

### Relationship to WP-2.1b's `min + quality*(max-min)`

WP-2.1b positions each stat roll deterministically within its `[min, max]` band as
`qualityScaledRoll(min, max, q) = min + q*(max-min)`, driven by `ItemInstanceInit.quality`. `QualityRoll`
**produces exactly that `q`.** So a crafted item's quality is the *same kind of number* a dropped item's
seeded roll is (a position in the band), and WP-3.1b sets `ItemInstanceInit.quality = QualityRoll(skill,
seed)` for a `NewItem` craft — feeding the WP-2.1b path with no second axis. `NewItem.qualitySkill` names
which skill's level drives the roll (null → the default `ItemInstanceData.DEFAULT_QUALITY = 0.5`); it is
3.1b **adapter metadata** — the pure `CraftPlanner`/`plan` ignore it and consume the already-resolved
`CraftContext.skillLevel`. `Transmute` **preserves** the input item's quality rather than re-rolling.

**Known coupling — `SKILL_CAP = 100` is a hardcoded global.** `QualityRoll` normalizes skill against a
single `SKILL_CAP = 100`, whereas `SkillDefinition.maxLevel` is per-skill. Today every skill is assumed to
cap at 100; if a skill ever caps elsewhere, its `frac` would saturate early/late. This is a deliberate,
documented placeholder: WP-3.1b's adapter may later pass the crafting skill's own `maxLevel` in place of
the constant (the formula takes `frac`, so only the normalizer changes). The number is tuned with crafting
content (roadmap 3.2), like the 0.1 power curve.

## Critical-craft chance

```
criticalChance(skill) = clamp(CRIT_BASE + CRIT_PER_SKILL * frac, 0, 1)   // CRIT_BASE=0.05, CRIT_PER_SKILL=0.20
isCritical(skill, seed) = splitmix64(seed XOR CRIT_SALT) < criticalChance(skill)
```

Critical-craft chance runs from **5% at skill 0 to 25% at the skill cap**, linear in skill. The decision
is a second deterministic uniform derived from a **salted** seed, so it is independent of the quality roll
for the same `(skill, seed)`. `CraftResult.Success.critical` carries the outcome; what a critical craft
*grants* (a quality bump, a bonus output, doubled yield, …) is a WP-3.1b runtime/content tuning decision —
this WP only ships the chance model and the deterministic decision. These numbers are placeholders in the
spirit of the 0.1 power curve and will be tuned alongside crafting content (roadmap 3.2).

## The pure planning result

`CraftPlanner.plan(recipe, ctx)` gates a recipe against a pure `CraftContext` (requirement state,
candidate inputs, optional target instance, balance, skill, seed, the station's permitted kinds) and
returns a pure `CraftResult`:

- `Success(outcome: OutcomePlan, consumption: List<ConsumedInput>, cost, quality, critical)` — the
  `consumption` is the **single source of truth** for what the craft removes: one `ConsumedInput` per
  satisfied ingredient, each naming exactly the matched candidate to remove — by `ItemKey` when the
  matched stack has RPG identity, else by `Material` for a plain vanilla stack. WP-3.1b removes strictly
  from this list and **never** re-derives anything from `Recipe.inputs`. This is what stops an RPG stack
  matched by a `MaterialTag`/`Category` ingredient from being consumed twice (once by key, once as a
  "vanilla" removal). Because both an `ItemKey` and a `Material` removal are expressible, vanilla
  ingredients need no separate inventory-layer pass.
- `Failure(reason)` — `DISALLOWED_OUTCOME` / `UNMET_REQUIREMENT` / `MISSING_INPUTS` /
  `INSUFFICIENT_FUNDS` / `NO_TARGET_ITEM` / `INVALID_TARGET`.

`CraftPlanner` matches ingredients **specific → general** (`Item` < `Predicate` < `Category` <
`MaterialTag`) before drawing down candidate counts, so a general ingredient never eats a stack a more
specific ingredient needed — a solvable craft is not failed by match order.

`OutcomePlan` is `Create(item, quality, count)` (NewItem / Transmute) or `Modify(result:
ItemInstanceData)` (every input-transforming outcome), computed by the pure `RecipeOutcome.plan(input,
quality)`. This mirrors the WP-2.1a precedent of shipping pure evaluation logic (`isMet`) in `api/` for
the impl to call: WP-3.1b's `CraftingServiceImpl` adapts the live craft onto a `CraftContext`, calls
`CraftPlanner.plan`, and applies the returned plan on the player's `TaskContext` (Folia rule 4).

## Deferred outcome runtimes (types ship now)

| Outcome | Type ships | Runtime lands |
| --- | --- | --- |
| `NewItem`, `UpgradeInput`, `Repair`, `Transmute` | WP-3.1a | WP-3.1b / WP-3.3a-b |
| `Reforge` | **WP-3.1a** | WP-3.3c |
| `InsertGem`, `AddSocket`, `RemoveGem` | **WP-3.1a** | WP-3.3d |
| `Enchant` | **WP-3.1a** | WP-3.4b |

`RecipeOutcomeApplicationTest` proves the deferred outcomes already compute the correct plan today (the
Reforge key / gem-at-index / enchant level is recorded in the plan); only the ItemStack-writing runtime is
deferred. Shipping the types now is exactly what keeps reforging, socketing, and enchanting on the one
recipe mechanism instead of a special path.
