# 2.1c — Requirement enforcement, inert items and lore

WP-2.1c adds the SINGLE inert-item path every item-based stat provider must consult, plus the lore
sections that show it to the player. It builds directly on WP-2.1a's `ItemRequirement`/`ItemRequirementState`/
`isMet` (definition-side gates, no enforcement) and WP-2.1b's `quality`/`durability`/`maxDurability`
instance fields (numbers only, no consequence yet).

## The single inert check

`api/items/Items.kt` adds:

```kotlin
enum class InertReason { UNMET_REQUIREMENT, ZERO_DURABILITY }

fun ItemDefinition.inertReason(instance: ItemInstanceData, state: ItemRequirementState): InertReason? {
    if (instance.durability <= 0) return InertReason.ZERO_DURABILITY
    if (requirements.any { !it.isMet(state) }) return InertReason.UNMET_REQUIREMENT
    return null
}

fun ItemDefinition.isInert(instance: ItemInstanceData, state: ItemRequirementState): Boolean =
    inertReason(instance, state) != null
```

This is the *only* place inert-ness is decided. Every item-based `StatProvider` calls it (directly, or via
a small per-provider pure `xStatsFor(...)` wrapper — see below) instead of re-deriving the concept. A
provider that skips this check is an exploit: it lets an under-leveled or zero-durability item silently
out-contribute every correctly-gated provider.

### `ZERO_DURABILITY` is wired here, not redefined by WP-2.2

The field (`ItemInstanceData.durability`) has existed since WP-2.1b with no consequence. This WP wires the
consequence (`durability <= 0` → inert) into the shared check, since the field already exists and the rule
is one line. **Nothing drains durability yet** — WP-2.2's job is exclusively to make `durability` reach
`<= 0` in the first place (the drain-on-hit mechanic). WP-2.2 must call into `inertReason`/`isInert` (or
rely on the providers that already do), not re-implement or redefine what "inert" means. Today, every
instance is created full (`durability == maxDurability`), so `ZERO_DURABILITY` cannot fire in practice
until WP-2.2 ships drain — this WP only proves the wiring is correct (`InertItemContributesNoStatsTest`
covers it explicitly with a `durability = 0` fixture).

## No-self-satisfaction rule

**The risk:** if `ItemRequirementState.statValue(stat)` for a candidate item reflected the player's *live,
fully-aggregated* stat snapshot (`StatService.snapshot`/`recalculateNow`), it would include that same
item's own contribution (via `EquipmentStatProvider`, plus any enchant/reforge/socket on it). A sword
granting `+50 Strength` with a `StatThreshold(STRENGTH, 20)` requirement would then always be "met" by its
own stats — the gate would be decorative. Worse, calling `StatService.snapshot` *from inside* one of its
own registered `StatProvider`s would recurse (`recalculateNow` iterates every registered provider,
including the one doing the calling).

**The rule:** `ItemRequirementState` is built by `requirementStateFor` (`core/listeners/EquipmentListener.kt`),
which deliberately never calls into `StatService.snapshot`/`recalculateNow` at all:

```kotlin
fun requirementStateFor(player: Player, services: ItemRequirementServices?): ItemRequirementState =
    object : ItemRequirementState {
        override fun skillLevel(skill: SkillKey): Int = services?.skillService?.level(player, skill) ?: 0
        override fun statValue(stat: StatKey): Double {
            val svc = services ?: return 0.0
            var value = svc.stats.definition(stat)?.defaultBase ?: 0.0
            for (def in svc.skillRegistry.all()) {
                val lvl = svc.skillService.level(player, def.key) - 1
                if (lvl <= 0) continue
                for (r in def.rewards) if (r is StatPerLevelReward && r.stat == stat) value += lvl * r.amountPerLevel
            }
            return value
        }
    }
```

- `skillLevel` reads `SkillService.level` directly. Skill levels are entirely item-independent (WP-2.1a
  already established this), so this is always safe.
- `statValue` returns the stat's registered `StatDefinition.defaultBase` (a single pure map lookup, e.g.
  `HEALTH`'s `100.0`) **plus** each skill's per-level `StatPerLevelReward` contribution for that stat — the
  same arithmetic `SkillStatProvider` applies, computed directly rather than through `StatService`. It
  deliberately EXCLUDES every item-based `StatProvider`'s contribution: equipment base stats,
  enchantments, reforge, sockets (and sets, once WP-5.3 lands) never count toward a `StatThreshold`. This
  is not just "the candidate item's own stats don't count" — no equipped item's stats count, from any
  slot. That is a stricter guarantee than the WP asked for (only the self-satisfaction case is called out
  as the named exploit), chosen because it is far simpler to implement correctly and impossible to get
  subtly wrong, and because it can never be *too lenient* (it can only under-count a stat that has
  significant item-based contributions, which makes a requirement *harder* to meet, never an exploit).
- Because this never calls `StatService.snapshot`/`recalculateNow`, it is safe to invoke from inside a
  `StatProvider.provideStats` — there is no recursion risk, and no need to duplicate `StatServiceImpl`'s
  ADD/MULTIPLY_BASE/MULTIPLY_TOTAL aggregation (rule 1 — no parallel stat path).

`InertItemContributesNoStatsTest` proves this empirically: it registers a `StatProvider` on a real
`StatServiceImpl` that reports `50.0` Strength for a player (simulating an item's own contribution being
the player's *entire* current Strength), confirms `StatService.snapshot` really does report `50.0`, and
then confirms `requirementStateFor(...).statValue(STRENGTH)` reports `0.0` regardless — so a
`StatThreshold(STRENGTH, 20.0)` requirement reads UNMET even though the "live" stat would trivially settle it.

## Building `ItemRequirementState` from a live player — the RamRPG.kt wiring gap

`ItemRequirementServices(skillRegistry, skillService, stats)` bundles what `requirementStateFor` needs.
Every one of the four item-based `StatProvider`s takes it as an **optional, defaulted-to-null trailing
constructor parameter**:

```kotlin
class EquipmentStatProvider(
    private val items: ItemInstanceService,
    private val defs: ItemDefinitionRegistry,
    private val requirementServices: ItemRequirementServices? = null,
) : StatProvider
```

This is optional, not required, for one reason: every one of these providers' construction call sites
lives in `RamRPG.kt` (`stats.registerProvider(EquipmentStatProvider(itemInstances, itemDefs), owner)`,
etc.), and this WP's file scope (rule 8 / B5) forbids touching `RamRPG.kt` — that file is wired centrally
by the orchestrator at merge time, not by an individual WP branch. Making the parameter optional keeps
every existing call site compiling unchanged.

**Consequence — read this before merging:** until the orchestrator updates those call sites to pass a real
`ItemRequirementServices(skillRegistry, skillService, stats)` (and, for `EnchantmentStatProvider` /
`SocketStatProvider`, also `itemDefs` — see below), `requirementStateFor` runs with `services = null` and
fails **closed**: `skillLevel` reads `0`, `statValue` reads `0.0`. Any item with a non-trivial
`SkillLevel`/`StatThreshold` requirement is therefore inert for everyone until wiring lands. This mirrors
WP-2.1a's `ItemRequirement.PerkOwned` fail-closed stub (`isMet` always `false` until `PerkService` exists):
a gate must never silently vanish just because its backing wiring isn't in place yet. Items with an empty
`requirements` list (most builtins below `UNCOMMON`, all tools) are completely unaffected — `isInert` only
consults `state` when `requirements` is non-empty.

**`EnchantmentStatProvider` and `SocketStatProvider` also gained an optional `defs: ItemDefinitionRegistry?
= null`** — before this WP neither took an `ItemDefinitionRegistry` at all (they only ever needed
`ItemInstanceData`), but the shared check is defined on `ItemDefinition` (`requirements` lives there), so
looking it up needs the registry. When `defs` is `null` or the key isn't found, these two providers cannot
evaluate the check at all and fail **open** (contribute normally) — a narrower, purely structural gap
distinct from the fail-closed evaluated-and-unmet case above. `EquipmentStatProvider` and
`ReforgeStatProvider` already took `defs` as a required parameter before this WP, so they have no such gap.

**Orchestrator TODO at merge** (`RamRPG.kt`, around the `stats.registerProvider(...)` block):

```kotlin
val reqServices = ItemRequirementServices(skillRegistry, skillService, stats)
stats.registerProvider(EquipmentStatProvider(itemInstances, itemDefs, reqServices), owner)
stats.registerProvider(EnchantmentStatProvider(itemInstances, enchantments, itemDefs, reqServices), owner)
stats.registerProvider(ReforgeStatProvider(itemInstances, itemDefs, reforges, reqServices), owner)
stats.registerProvider(SocketStatProvider(itemInstances, gems, itemDefs, reqServices), owner)
```

`EquipmentListener`'s own constructor is untouched (still just `StatService`) — it does not need any of
this wired into it; see the next section.

## Why `EquipmentListener.kt` needs no new listener hook

`ItemRequirementServices` and `requirementStateFor` live in `core/listeners/EquipmentListener.kt` as
file-scope declarations (the same pattern as this file's existing `applyPlayerAttributes` free function) —
this is the "build an `ItemRequirementState` from the wearer" piece of the WP's file scope. Per rule 2
("don't add a bespoke listener hook for gameplay beyond the equipment-change refresh"), the *refresh* was
already there: every event this listener handles already calls `stats.markDirty(...)` followed by
`applyAttributes` → `StatService.recalculateNow`. Since `requirementStateFor` is a pure, cheap, no-cache
computation invoked fresh by each provider on every `provideStats` call, that existing recalculation *is*
the inert-ness refresh — there is no separate cache to invalidate and nothing new to hook. `isInert` is
also never persisted onto `ItemInstanceData` (rule 5 — no new instance fields); it is always recomputed.

## Testable-without-a-server: extracting each provider's per-stack logic

`EquipmentStatProvider`, `EnchantmentStatProvider`, `ReforgeStatProvider`, and `SocketStatProvider` all
need `ctx.player.equipment` (a live `org.bukkit.entity.Player`'s `EntityEquipment`) to find what's
equipped — exercising that end-to-end needs a live server or extensive Bukkit proxy fakery. Per rule 10 and
the "pure, off-server" test requirement, each provider's per-stack contribution logic was extracted into a
top-level `internal fun xStatsFor(def, data, state, ...): List<StatModifier>` (`equipmentStatsFor`,
`enchantmentStatsFor`, `reforgeStatsFor`, `socketStatsFor`) that takes a plain `ItemDefinition` +
`ItemInstanceData` + `ItemRequirementState` and returns the stat modifiers directly — no `Player`, no
`ItemStack`, no registry lookups beyond the small typed registries (`EnchantmentRegistry`, `ReforgeRegistry`,
`GemRegistry`) each already needed. `provideStats` is now a thin loop over `equippedStacks`/the equipment
slots calling the pure function per stack. `InertItemContributesNoStatsTest` calls these functions directly:
a single missed `isInert` check in any one of them would make that provider return a non-empty list for an
inert item, which is exactly what each "withholds ... on an inert item" test asserts against.

## Lore sections

Three new `LoreSection`s in `api/items/Items.kt`, added to `LoreTemplate.DEFAULT` in this order (after
`Enchantments`, before `RarityLine` — a footer-style "meta" block just above the rarity/quality line, the
same place Hypixel-style RPG item lore conventionally puts item-level/requirement/durability info):

```
Stats, ReforgeLine, SocketsLine, Description, Enchantments, Requirements, ItemLevel, Durability, RarityLine
```

- **`Requirements`** — one line per `ItemDefinition.requirements` entry, colored GREEN when
  `requirement.isMet(state)` and RED otherwise, using `LoreContext.requirementState` (a new, additive,
  default-`null` field). If any requirement is unmet, an extra bold dark-red banner line
  (`ramrpg.item.inert`) is appended. **When `requirementState` is `null`** (no caller has wired a live
  state into `LoreContext` yet — see below), every requirement renders as unmet. This mirrors the
  fail-closed default used everywhere else in this WP: a requirement line must never *look* satisfied
  just because the real state wasn't plumbed through.
- **`ItemLevel`** — a single gray `ramrpg.item.level` line showing `ItemDefinition.itemLevel`.
- **`Durability`** — a `ramrpg.item.durability` line (`current/max`), RED instead of GRAY at zero, plus the
  same shared `ramrpg.item.inert` banner appended when depleted. (The banner text/key is identical whether
  triggered by `Requirements` or `Durability`; if somehow both conditions hold at once the banner would
  render twice, which is a harmless duplication with zero cost in the durability-drain-less world of this
  WP — WP-2.2 or a later cleanup can dedupe centrally if it ever becomes visible.)
- **`RarityLine` now also renders quality.** `LoreRender.rarity` appends the WP-2.1b placeholder
  quality-tier band (Crude/Rough/Standard/Fine/Superior/Masterwork, see
  [2.1b-quality-durability.md](2.1b-quality-durability.md)) next to the bold rarity name, via six new
  `ramrpg.item.quality.*` keys. This is the first WP to render that placeholder table — 2.1b explicitly
  deferred rendering to "a later WP."

### Not wired: `PacketItemRenderer.kt`

`LoreContext.requirementState` (and the new `skillNameLookup` field) default to safe no-ops so
`PacketItemRendererImpl`'s existing `LoreContext(...)` construction (named arguments, in
`core/rendering/PacketItemRenderer.kt`) keeps compiling unchanged — that file is **not** in this WP's file
scope. Consequently, real in-game lore does not yet show live-per-viewer requirement met/unmet
styling — every live-rendered item's `Requirements` section renders as unmet (fail-closed, per the rule
above) until a future WP (or the orchestrator, if trivial) passes a real `requirementState`/
`skillNameLookup` into `PacketItemRendererImpl.renderUncached`'s `LoreContext` construction, built via
`requirementStateFor(viewer, ...)`. All three new sections' logic, rendering, and styling rules are fully
covered by `RequirementLoreRenderTest`/`QualityInRarityLineTest` at the pure `LoreContext`/`LoreSection`
layer regardless.

## Providers touched (not just `StatProviders.kt`)

The roadmap prompt's file list names only `core/services/StatProviders.kt` for
"`EquipmentStatProvider`, `EnchantmentStatProvider`, `ReforgeStatProvider`, `SocketStatProvider`", on the
assumption all four live in that one file. In the actual tree, only `EquipmentStatProvider` and
`EnchantmentStatProvider` are in `StatProviders.kt`; `ReforgeStatProvider` and `SocketStatProvider` are
each in their own file (`ReforgeStatProvider.kt`, `SocketStatProvider.kt`). Since "every item-based
provider must consult the same inert check" is this WP's central, non-negotiable goal regardless of file
layout, both of those files were modified too — the file-scope violation is in service of the literal
DONE criterion ("a reviewer will grep for four copies vs one"), not a substitute for it. No other files
were touched to reach the four providers.

## Sets (WP-5.3, future)

`SetStatProvider` does not exist yet. When it lands, it must consult the exact same
`ItemDefinition.isInert`/`inertReason` function (and take the same optional
`requirementServices`/`defs` shape) as the four providers here — an inert item must not count toward a set
bonus threshold either.
